Operation card template: the fields to include

A card without an owner, a date and a revision is a sketch. These are the fields that make it usable.

Short answer

A complete operation card names the property, the system and the unit, the date, who handled it and a signature. It carries a page number, a revision table and a reference back to the plan, so the next technician can find the drawing and see what changed.

Property, system and unit

The title block starts with the project name, which is where the property belongs. Then name the system and the unit, for example the air handling unit LB01, so the card can be filed and found by the same designation the rest of the documentation uses. The built-in template has fields for Project name, System, Operation card and Assignment no.

Use one card per system. A card that mixes two units is hard to revise and harder to hand over, because a change to one unit forces a new revision of both.

Date, handled by and signature

The card needs to say when it was produced or checked, who did the work and who signed it. The template provides Date, Handled by/Consultant and Sign. A date without a name is not traceable, and a name without a date cannot be placed in the project's history.

The signature is not decoration. It marks the point where someone accepted that the schematic matches the installation. If the card is later changed by someone else, the revision table records that too, and the original sign-off stays in the revision table.

Page and revision

The Page field is free text, prefilled with the sheet's ordinal and never renumbered automatically. Write the page designation the property actually uses, and check it after sheets are inserted or removed. Do not use the page number as the unit designation; the unit's own tag belongs in the system field.

The revision table is where changes are recorded. Each row carries the reference, what the revision refers to, the date and a signature. Add a row whenever a component, setpoint or control strategy changes, even if the drawing itself looks the same.

The reference back to the plan

An operation card is schematic, not architectural, so it cannot show where the unit sits in the building. The Ref. and Rev. refers to fields connect the card to the plan: the drawing number, the room or the detail that the reader needs in order to find the physical installation.

Write the reference the same way the drawing set writes it. A room number alone is not enough if the plan has several buildings, and a drawing number alone is not enough if the reader does not know which revision of the plan is current.

Before you export

Open Edit sheet fields…, or double-click a cell, and fill every field that applies. Check that the revision row matches the change you made, and that the reference points at the plan revision that is actually in use. Then export the drawing PDF.

Sheet fields are drawn into the PDF even when every layer is hidden, and the exported text is searchable. Hiding a layer never hides the title block or the data table, so a clean export still carries its ownership and revision.

Common mistakes

  • Filling the title block after the drawing, so the card has no date, owner or revision.
  • Using the page number as the unit designation instead of the system's own tag.
  • Adding a component without adding a revision row.
  • Expecting the free-text Page field to renumber itself when sheets are inserted.

Questions

Is there a required operation card standard?

GridScalr does not enforce one format. The built-in template provides a title block and revision table; adapt the field values to the documentation practice of the property.

Does the Page field update automatically?

No. It is free text, prefilled with the sheet ordinal, and it is not renumbered when sheets are added or removed.

Are the sheet fields exported when layers are hidden?

Yes. Sheet fields are drawn into the PDF even when every layer is hidden, and the exported text is searchable.
