- No rendering, export, import or package change; no auto-deletion; no source

## Phase 4 — derived-PDF cache lifecycle

- **Issue:** [#256](https://github.com/MajorJohnDoe/gridscalr/issues/256) (phase 4 of 4)
- **PR:** [#265](https://github.com/MajorJohnDoe/gridscalr/pull/265)
- **Branch:** `feat/256-derived-pdf-cache`
- **Commit:** `bcf2891` (implementation and docs); the handover commit follows on the same branch
- **Schema:** stays 27
- **Status:** PR open, awaiting conductor review

### Completed work

- **Cache location and key.** A derived PDF lives in the sibling folder
  `<project stem>.derived/` with the key in the file name
  (`<sha256 first 16>-v<converterVersion>-p<pageCount>.pdf`). The folder is
  derived in Rust from the project path, so a cache can only be written beside
  its own project. `src-tauri/src/derived_cache.rs` decodes, size-caps, verifies
  as a PDF, writes through a flushed temporary sibling, re-hashes the final file
  and refuses a protected source path or a symlinked folder.
- **Lifecycle.** `src/features/derivedPdfCache/` builds on import into a saved
  project and on save for an embedded document whose scan is reachable, stores
  the `derivedPdf` marker, reuses a current cache on open, rebuilds silently on a
  missing or stale key, and refuses a scan whose SHA-256 does not match. A
  converter-version-only mismatch still opens a present cache when the scan is
  gone, because the drawing revision is unchanged.
- **Missing scan.** One localized dialog names the document and the expected
  path and offers **Locate the scan…**; a located TIF is checksum-validated and
  rebuilt. The project is not opened on a blank page, and a TIF marker document
  no longer falls through to the PDF picker (which used to change its kind).
- **Passthrough.** `TiffConversion.passthrough` and
  `DocumentSourceInfo.passthrough` record a document whose every page kept its
  compressed strips (CCITT G3/G4 or JPEG-in-TIFF). It stays embedded, never
  acquires a cache entry, and the CCITT per-strip bytes are untouched.
- **Rendering paths.** The main loader, the reference pane and revision
  comparison, and the project import source all resolve a marker through the
  same `loadDerivedPdfBytes()`. The import picker marks a TIF available when its
  cache exists or its scan can rebuild it (F-113).
- **Packages.** A cache-backed scan ships its derived cache under `derived/`
  and its original scan is never included; an embedded scan may still include
  its scan under `source-scans/`. The manifest gains `derivedCaches` with
  `kind: "derived"` (Rust + TS), the README states the rule, extraction and
  inspection accept the section, and the packaged project rewrites
  `derivedPdf.relativePath` to the archive path.
- **Enforced budget.** `evaluateDerivedCacheBudget()` warns once per changed
  state at 160 MiB of derived cache or when JSON plus cache approaches the
  256 MB project limit; the save is never blocked. Measured reference project (6
  × A2-class colour sheets, 4960 × 3508 at 300 DPI): **79.19 MiB embedded JSON →
  0.01 MiB cached JSON**, with 59.39 MiB of cache on disk
  (`GRIDSCALR_DERIVED_BENCH=1 npx vitest run tests/derivedPdfBudget.test.ts`).
- **Docs.** ADR 0015 moved from deferred to implemented with the failure-mode
  table and the measurement; `docs/limitations.md`, `docs/user-guide.md`,
  `docs/project-file.md`, `docs/architecture.md`, `AGENTS.md` and `README.md`
  updated.

  `README.md`, `AGENTS.md`, `docs/plan/{0.28,foundation-findings}.md`

### Decisions

- A cache is only written from bytes the current converter produced. An embedded
  document is converted again from its scan at save time rather than stamping
  the current converter version on bytes an older release produced (keeps the
  phase 3 rule honest). If the scan is unreachable, the bytes stay embedded.
- The cache folder is `<project stem>.derived/`, not `<project stem>.drawings/`,
  so the managed-copy inventory and its **Remove unused drawings…** action never
  see a cache, and no cache is deleted automatically.
- A converter-version-only mismatch opens a present cache when the scan is gone;
  any source-hash or page-count mismatch is a rebuild, never trust.
- The budget is a warning, not a refusal; the 256 MB project limit stays the
  only hard stop.
- No schema bump (stays 27), no new source storage mode, no source write.

## Phase 6 — automated macOS artifact verification

- **Issue:** [#74](https://github.com/MajorJohnDoe/gridscalr/issues/74)
- **PR:** [#269](https://github.com/MajorJohnDoe/gridscalr/pull/269)
- **Branch:** `tooling/74-macos-artifact-check`
- **Commit:** `8059729` (implementation and docs); the handover commit follows on the same branch
- **Schema:** stays 27
- **Status:** PR open, awaiting conductor review

### Completed work

- **macOS job.** After staging, `Verify the macOS disk image and app bundle`
  runs `scripts/verify-macos-bundle.mjs`. It hashes both staged files and checks
  `SHA256SUMS-macos.txt` against them, mounts the DMG with `hdiutil attach` at a
  temporary mount point, requires `GridScalr.app` and
  `Contents/MacOS/gridscalr`, requires `lipo -info` to report `x86_64` and
  `arm64`, matches `CFBundleShortVersionString` to `package.json` and
  `CFBundleIdentifier` to `com.gridscalr.desktop`, repeats every check on the
  `.app.zip` extracted with `ditto -x -k`, and detaches in a `finally` block.
  Failures are `::error::` lines and the step exits 1.
- **License prompt.** Tauri embeds `bundle.licenseFile` (`LICENSE`) as the
  disk-image license agreement, so `hdiutil attach` prints the MIT license and
  asks **Agree Y/N**. With a non-interactive stdin it cancels
  (`hdiutil: attach canceled`). There is no `-acceptlicense` on the hosted
  macOS 26 runner, so the step writes the answer to stdin, which is what
  `yes | hdiutil attach` does.
- **Merged checksums.** The `checksums` job gains `actions/checkout` and
  `actions/setup-node` and runs `scripts/verify-release-checksums.mjs`, which
  recomputes every downloaded artifact's SHA-256 and requires the merged
  `SHA256SUMS.txt` to list each file exactly once with the matching hash, with
  both macOS names required. Listed-but-absent, present-but-unlisted,
  duplicate, malformed and wrong-hash lines all fail.
- **Rules and tests.** `scripts/release-artifact-rules.mjs` (with `.d.mts`) owns
  the pure decisions and `tests/releaseArtifactCheck.test.ts` (17 tests) proves a
  thin binary, an unreadable `lipo` result, a missing app or executable, a wrong
  identity, a missing or stale version, and every checksum failure, plus the
  workflow wiring: the macOS-only guard, the merged-checksum step, and no
  `--smoke-test` in any executable line.
- **Docs.** `docs/releasing.md` gains section 4a and the merged-checksum rule,
  and step 7 marks the macOS install unverified; `docs/limitations.md` records
  the CI-only verification and that the release job never launches a packaged
  binary; `docs/testing.md`, `README.md`, the `AGENTS.md` script map and release
  bullet, and F-117 are updated.

### Decisions

- **The packaged `--smoke-test` run is not kept, because it does not exist.** The
  phase scope asked to keep it as the launch proof, but the smoke commands are
  compiled under `#[cfg(debug_assertions)]` (F-037) and the release job stopped
  launching release binaries after the 0.24.0 hang (F-074). Re-adding it would
  reintroduce a P1 hang. The macOS launch proof stays the debug packaged smoke
  test in `ci.yml` on every pull request; the release job proves mount,
  universal binary, identity, version and hashes. Recorded as **F-117**.
- The check pins the bundle identifier and version, not just the presence of an
  app, so a renamed or stale bundle cannot pass.
- The macOS names are derived from `package.json`, so a staging rename fails both
  the macOS job and the merged-checksum check.
- No signing or notarization ([#56](https://github.com/MajorJohnDoe/gridscalr/issues/56)
  stays in the backlog), no build-matrix or artifact-name change, no schema
  change (stays 27), no version bump.

### Findings

- **F-117** recorded (P3, accepted): the macOS release artifact has no launch
  proof, so release-profile runtime failures are unverified; the physical
  Apple-hardware install stays a documented limitation.
- No other findings.
