# Refactor pre-flight and CSS theme readiness for 0.20

**Status:** proposed 2026-11-07. Reviewed against the codebase on 2026-11-07.
Theme decisions recorded 2026-11-07: jade stays the default; light, grey and navy
are optional; themes may change only UI chrome and the canvas background, never
the drawing-board content or the export. Documentation screenshots stay on the
default theme. Steps 0–4 completed 2026-11-07; the #60 extractions are next.
**Scope:** the safety net, module boundaries and stylesheet structure needed before
issue [#60](https://github.com/MajorJohnDoe/gridscalr/issues/60) starts, plus a
theme-ready CSS architecture. Theme implementation is deliberately deferred.
**Related:** [#60](https://github.com/MajorJohnDoe/gridscalr/issues/60),
[#61](https://github.com/MajorJohnDoe/gridscalr/issues/61),
[#52](https://github.com/MajorJohnDoe/gridscalr/issues/52),
[#23](https://github.com/MajorJohnDoe/gridscalr/issues/23),
[#63](https://github.com/MajorJohnDoe/gridscalr/issues/63),
ADR [0001](../adr/0001-feature-modules.md), ADR [0005](../adr/0005-large-project-performance.md).

If the code and this plan disagree, stop and surface the conflict rather than
silently choosing one.

## 1. Goal

Make the #60 refactor safe, reviewable and hard to undo, without changing user
behaviour:

- a clean, released baseline;
- automated coverage of the flows that will be extracted;
- enforced module boundaries so the integration files cannot regrow;
- a stylesheet split with one semantic token layer, ready for themes later;
- an explicit sequence against #52, #23 and #63, which touch the same files.

Success means the first #60 extraction can be reviewed as a mechanical move with
tests before and after, and that adding a theme later is a token-file change rather
than a rewrite.

### Test coverage of the integration points

- No test in `tests/` imports `App.ts` or `CanvasView.ts`. Vitest runs in the
  `node` environment and covers model, I/O, project-file, PDF, report and geometry
  logic.
- CI runs `test:ui`, `test:canvas`, `test:count` and `test:touch` against the
  browser fallback, plus a packaged Tauri smoke test.
- The Tauri smoke flow `runSmokeTest` already covers: open the bundled demo, save,
  reopen, mutate, show the unsaved-changes prompt, cancel and keep the project.
- Native-only paths are not covered: drag-and-drop, recent files, native dialogs,
  password handling, checksum verification, file association and window state.
- Playwright scripts drive the running app; they give behaviour coverage, not unit
  coverage of `App.ts` or `CanvasView.ts`.

### Module enforcement

- ADR 0001 defines feature modules, but ESLint has no import-boundary rule and no
  `max-lines` budget. Nothing prevents a feature from importing `App.ts` or
  `CanvasView.ts`, or a new 2,000-line file from appearing.
- `AGENTS.md` states the rule in prose only.
- There is one existing type-only import to decide on: `src/ui/splitView.ts`
  imports `type { CanvasView } from "../canvas/CanvasView"`. It holds a reference
  instance and does not call integration logic directly.

### Stylesheet and themes

- `src/main.ts` imports three stylesheets, in this order:
  `./styles.css`, `./styles/help.css`, `./styles/popovers.css`.
- `src/styles.css` has 32 custom properties in `:root`, 69 raw hex colours and 114
  `rgb`/`rgba` occurrences. `help.css` has 1 hex and 5 `rgb`/`rgba`;
  `popovers.css` has 0 hex and 5 `rgb`/`rgba`.
- The custom-property block is at the top, but the rest of the file is sectioned by
  feature, not by layer. Media queries are interleaved: `@media` blocks at lines
  4335, 4472, 4508 and 4563, with more rules after them. Moving all responsive
  rules to the end would change the cascade.
- `src/main.ts` imports one root stylesheet, so cascade order is implicit.
- `color-scheme: dark` is fixed; there is no `data-theme` hook.
- The boot fallback in `index.html` hardcodes dark colours, including `#14181b`,
  `#1e2428`, `#35c2a1` and `#e8eef1`.
- `src-tauri/tauri.conf.json` hardcodes the native window background as
  `#14181b`.
- Canvas, model and inline styles contain roughly 80 raw hex colours plus dynamic
  `style.background`/`style.color` assignments. These are not connected to CSS
  tokens.
- `docs/theme-preview/` already contains design previews: `light.css` (light
  chrome, white panels, jade accent), `navy.css` (blue-shifted dark chrome, jade
  accent), a shared `chrome.css` with preview variables, and review screenshots.
  `scripts/theme-preview.mjs` injects the palettes over the shipped dark theme.
  Neither the script nor the directory is referenced from `package.json` or the
  documentation. `chrome.css` explicitly says its rules should move into
  `src/styles.css` when real themes land.

#### Desktop-only manual checklist

These flows cannot be driven by the browser fallback and are not covered by the
packaged smoke test. Re-run them before and after the project-session extraction:

- open a PDF/TIF through the native dialog, including a password-protected PDF;
- save, Save as, and a rejected write to a source drawing path;
- open a recent project and a recent drawing, then remove a missing entry;
- drag a `.gridscalr`, PDF and unsupported file onto the window;
- open a `.gridscalr` from the file manager and confirm single-instance focus;
- close with unsaved changes through Save, Discard and Cancel;
- restore window size and position, then quit from the window controls;

### D. Stylesheet split and theme-ready tokens

Do this in two separate phases. The first phase must be pixel-identical.

#### D1. Token layer and split (in scope for 0.20)

**Completed 2026-11-07.** The stylesheet is split mechanically, the token
contract and `data-theme="default"` hook are in place, and the screenshots are
refreshed. Full literal migration is deferred to D2, where the remaining
gradients, shadows and alpha variants are replaced together with the theme files
instead of being turned into value-named tokens now.

The split must preserve the cascade exactly. Do **not** reorganise by semantic
layer and move media queries in the same PR.

1. Inventory every colour in `src/styles.css`, `help.css`, `popovers.css` and the
   inline/TS palettes, and map it to a semantic role:
   `--surface-app`, `--surface-panel`, `--surface-raised`, `--surface-sunken`,
   `--text-primary`, `--text-muted`, `--border-default`, `--border-soft`,
   `--accent`, `--accent-strong`, `--status-danger`, `--status-warning`,
   `--status-success`, `--selection`, `--focus-ring`, `--scrollbar`,
   `--shadow-*`.
   Reuse the token names already present in `docs/theme-preview/light.css` and
   `chrome.css`; do not invent a second vocabulary.
2. Keep the existing `--jade`, `--cyan`, `--amber` names as aliases during the
   migration so component rules do not all change at once.
3. Split mechanically by **contiguous line ranges**, in the current order. Map each
   range to a file using the existing section comments, but do not reorder rules:
   ```text
   src/styles/tokens.css       :root token block, aliases and theme contract
   src/styles/base.css         reset, typography, scrollbars, shared utilities
   src/styles/shell.css        top bar, window chrome, workspace, docks,
                               symbol library, canvas, welcome
   src/styles/panels.css       inspector, layers, pages, markups, status bar
   src/styles/dialogs.css      modal, export/import/category dialogs, toast,
                               quantities, menu bar, settings, preferences,
                               diagnostics, measurement dialogs
   src/styles/markups.css      Markups panel, revision compare, text search
   ```
   Keep every `@media` block inside the file where it appears today. A later PR may
   regroup responsive rules only with a visual-regression gate and a separate
   approval.
4. `src/main.ts` imports the parts in the same order, followed by the existing
   `help.css` and `popovers.css`:
   ```ts
   import "./styles/index.css";
   import "./styles/help.css";
   import "./styles/popovers.css";
   ```
   `src/styles.css` may remain temporarily as a barrel that imports the new files,
   then be removed. Do not keep both paths loading the same rules.
5. If `src/styles.css` is removed, update `scripts/docs-fingerprint.mjs`, which
   lists it in `ROOT_FILES`. The script already scans `src/styles/**` recursively,
   so the new files are covered.
6. Use `docs/theme-preview/chrome.css` as the inventory of chrome rules that
   still hardcode colours. Do not merge it wholesale in D1; move a rule only when
   the token value is known and the result stays pixel-identical, otherwise defer
   it to D2. Keep the preview palette files and screenshots as design references.
7. Update `docs/architecture.md` with the new stylesheet map.

**Acceptance:** the mechanical split preserves the cascade, `npm run docs:capture`
produces the same screenshots (or only expected anti-aliasing noise),
`npm run check:docs` passes, the fingerprint is updated, and `styles.css` is not
loaded twice. The core palette is tokenised in `tokens.css`; migrating the
remaining decorative gradients, shadows and alpha variants is part of D2.

#### D2. Theme implementation (later, not in 0.20)

Decisions already taken:

- The current dark jade theme is the default. Light, grey and navy are additional
  options chosen in Options/Preferences; none of them replaces the default.
- “Blue” means navy; `docs/theme-preview/navy.css` is its basis.
- A theme must not change anything on the drawing board. The only exception is the
  canvas surround/background, which may change slightly with the theme.
- The canvas background is screen-only and must never appear in print or PDF
  export.
- Documentation screenshots stay on the current default theme for now.
  Theme-specific screenshots are a later task, not part of the theme entry work.

When that work starts, each theme is one token file under `src/styles/themes/`:

```text
src/styles/themes/default.css      current dark jade
src/styles/themes/light-green.css  light surface, green accent (preview: light.css)
src/styles/themes/grey.css         neutral grey
src/styles/themes/navy.css         navy surfaces (preview: navy.css)
```

#### Canvas and export boundary

- **Drawing board:** grid, selection, handles, marquee, labels, measurements,
  annotations, symbols and every other drawing element keep fixed colours in all
  themes. Only the canvas surround/background may vary.
- **UI chrome:** top bar, rail, panels, dialogs, menus and status bar follow the
  theme.
- **Export:** print and PDF always use the fixed document palette. The canvas
  background is never exported. Switching theme must not change the exported
  result.

Symbol category and inspection colours remain drawing content until issue #112
decides per-symbol colour.

Open decisions for that phase:

- whether the theme follows the OS (`prefers-color-scheme`), is chosen in
  Preferences, or both;
- how to apply the stored theme before first paint. `index.html` has
  `script-src 'self'`, so an inline bootstrap script violates CSP; use a small
  external script such as `public/boot-theme.js`, or accept a documented flash;
- whether the native window background in `src-tauri/tauri.conf.json` follows the
  theme, and how to update it at runtime without a restart;
- how much the canvas background may vary while keeping the drawing board
  readable;
- contrast target (WCAG AA for text and controls);
- whether `docs/theme-preview` stays as a design artefact or moves fully into the
  shipped theme files.

Add an `npm run theme:preview` script and document `docs/theme-preview` so the
existing review tooling is discoverable.

**Non-goals in D2:** user-authored themes, per-project themes and a theme
marketplace.

## 6. Risks

| Risk | Mitigation |
| --- | --- |
| Refactor changes behaviour that no test covers | characterisation tests and manual desktop checklist first |
| CSS split changes the cascade | mechanical contiguous split, no reordering, media queries stay in place |
| `docs-fingerprint.mjs` breaks when `styles.css` is removed | update `ROOT_FILES`; `src/styles/**` is already scanned |
| Screenshots look stale after the split | run `docs:capture`, review the manifest and pixel diff |
| Large files regrow | ESLint boundary and size budgets |
| Type-only imports fail the boundary rule | use `@typescript-eslint/no-restricted-imports` with `allowTypeImports`; document `splitView.ts` |
| Parallel work on the same files | merge order above; rebase before starting a seam |
| Over-refactoring | one seam per PR, no behaviour change, no new features |
| Theme scope creep | D2 is explicitly out of scope; only the token contract is prepared |
| Theme flashes at boot | external CSP-safe bootstrap script, native window background decision |
| Existing theme previews drift or are forgotten | reference `docs/theme-preview` in the plan and add `npm run theme:preview` |
| Playwright flakiness | keep scripts deterministic, publish failure artifacts |
| Desktop-only flows remain untested | document the manual checklist and extend the Tauri smoke where cheap |

## 7. Definition of done for the pre-flight

- 0.19.3 is released and `main` is clean.
- Coverage report runs in CI with no threshold yet.
- Every #60 extraction target has a regression test or a manual checklist entry.
- ADR 0008 exists and ESLint enforces the import direction.
- Styles are split mechanically behind a semantic token layer with
  `data-theme="default"`, and `help.css`/`popovers.css` are still loaded in order.
- Screenshots are unchanged by the CSS split and the fingerprint is updated.
- #60 is sliced into sub-issues and #59 is corrected.
- The theme roadmap is recorded here, `docs/theme-preview` is documented, and no
  theme is added.

## 8. Out of scope

- New user-facing features.
- Project schema or app-version changes.
- Performance optimisation itself (#52).
- Reference-pane navigation (#23).
- Shell status and small-screen work (#63).
- Implementing light, grey or blue themes.
