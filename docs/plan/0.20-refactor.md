# Refactor pre-flight and CSS theme readiness for 0.20

**Status:** proposed 2026-11-07. Reviewed against the codebase on 2026-11-07.
Theme decisions recorded 2026-11-07: jade stays the default; light, grey and navy
are optional; themes may change only UI chrome and the canvas background, never
the drawing-board content or the export. Documentation screenshots stay on the
default theme. Steps 0–25 completed 2026-11-07. CanvasView still owns the pointer
event listeners, but the pointer host, helper layer, marquee, pan, drag, transform,
creation and touch gestures are extracted. The remaining work is planned in sections
3.G and 3.I: context-menu and the final cutover, with the file-budget gate already
enforced.
**Scope:** the safety net, module boundaries and stylesheet structure needed before
issue [#60](https://github.com/MajorJohnDoe/gridscalr/issues/60) starts, plus a
theme-ready CSS architecture. Theme implementation is deliberately deferred.
**Related:** [#60](https://github.com/MajorJohnDoe/gridscalr/issues/60),
[#61](https://github.com/MajorJohnDoe/gridscalr/issues/61),
[#52](https://github.com/MajorJohnDoe/gridscalr/issues/52),

If the code and this plan disagree, stop and surface the conflict rather than
silently choosing one.

## 1. Goal

Make the #60 refactor safe, reviewable and hard to undo, without changing user
behaviour:

- a clean, released baseline;
- automated coverage of the flows that will be extracted;
- enforced module boundaries so the integration files cannot regrow;
- a stylesheet split with one semantic token layer, ready for themes later;
- an explicit sequence against #52, #23 and #63, which touch the same files.

Success means the first #60 extraction can be reviewed as a mechanical move with
tests before and after, and that adding a theme later is a token-file change rather
than a rewrite.

#### D2. Theme implementation (later, not in 0.20)

Decisions already taken:

- The current dark jade theme is the default. Light, grey and navy are additional
  options chosen in Options/Preferences; none of them replaces the default.
- “Blue” means navy; `docs/theme-preview/navy.css` is its basis.
- A theme must not change anything on the drawing board. The only exception is the
  canvas surround/background, which may change slightly with the theme.
- The canvas background is screen-only and must never appear in print or PDF
  export.
- Documentation screenshots stay on the current default theme for now.
  Theme-specific screenshots are a later task, not part of the theme entry work.

When that work starts, each theme is one token file under `src/styles/themes/`:

```text
src/styles/themes/default.css      current dark jade
src/styles/themes/light-green.css  light surface, green accent (preview: light.css)
src/styles/themes/grey.css         neutral grey
src/styles/themes/navy.css         navy surfaces (preview: navy.css)
```

#### Canvas and export boundary

- **Drawing board:** grid, selection, handles, marquee, labels, measurements,
  annotations, symbols and every other drawing element keep fixed colours in all
  themes. Only the canvas surround/background may vary.
- **UI chrome:** top bar, rail, panels, dialogs, menus and status bar follow the
  theme.
- **Export:** print and PDF always use the fixed document palette. The canvas
  background is never exported. Switching theme must not change the exported
  result.

Symbol category and inspection colours remain drawing content until issue #112
decides per-symbol colour.

Open decisions for that phase:

- whether the theme follows the OS (`prefers-color-scheme`), is chosen in
  Preferences, or both;
- how to apply the stored theme before first paint. `index.html` has
  `script-src 'self'`, so an inline bootstrap script violates CSP; use a small
  external script such as `public/boot-theme.js`, or accept a documented flash;
- whether the native window background in `src-tauri/tauri.conf.json` follows the
  theme, and how to update it at runtime without a restart;
- how much the canvas background may vary while keeping the drawing board
  readable;
- contrast target (WCAG AA for text and controls);
- whether `docs/theme-preview` stays as a design artefact or moves fully into the
  shipped theme files.

Add an `npm run theme:preview` script and document `docs/theme-preview` so the
existing review tooling is discoverable.

**Non-goals in D2:** user-authored themes, per-project themes and a theme
marketplace.

### G. Pointer controller (follow-up to step 10)

The pointer event handlers are still in `CanvasView.ts`. Gesture state, group
handles and interaction drawing are extracted, but `onPointerDown/Move/Up` still
reach into canvas fields. This is the last large behavioural seam and needs its own
design and staged PRs.

**Status:** P0–P4 complete 2026-11-07. `PointerController`, `PointerHost`, the moved
`pointerState.ts` and `groupHandles.ts`, the helper layer, marquee, pan, item drag,
vertex editing, transform gestures, creation-tool pointer-down branches,
double-click editing, pen priority and touch navigation are extracted. P5–P6 remain.

#### Target ownership

`CanvasView` keeps the scene: renderer, canvases, page sizes, hit testing, editors,
draft creation, crop mode and public test API. A new `PointerController` owns:

- DOM pointer, wheel, double-click and context-menu listeners;
- gesture state: drag, marquee, pan, pointer position, snap cache and touch
  long-press;
- hover state: handle, label resize and label connection;
- pen priority and palm suppression;
- the decision of which gesture a pointer event starts and which host command it
  calls.

Proposed module layout:

```text
src/canvas/pointer/
  PointerController.ts   event binding, state machine and dispatch
  PointerHost.ts         the explicit host interface CanvasView implements
  gestures.ts            drag, marquee, pan and touch transitions
  targets.ts             handle, label, item, crop and search-hit resolution
```

`pointerState.ts` and `groupHandles.ts` move under `pointer/` in the first PR. The
controller may import `store` and `src/model`, but not `CanvasView`.

#### Host interface

`PointerHost` is the only integration surface. It exposes the scene facts and
commands the controller needs:

- geometry: `view`, `page`, `zoom`, `toScreen`, `toPage`, `pageSize`,
  `ensurePageSize`, `readOnly`;
- rendering: `invalidate`, `updateCursor`, `capturePointer`, `releasePointer`;
- editors and drafts: `editors`, `draft`, `startDraft`, `finishDraft`,
  `cancelDraft`, `removeLastPoint`;
- item creation: `createItem`, `createCallout`, `editItemText`,
  `promptVolumeDepth`, `runCalibration`, `editCalibration`, `finishQuickArea`,
  `finishPen`, `finishShape`;
- overlays: `pageLabelLayouts`, `labelResizePoint`, `annotationScreenPoint`,
  `commitLabelConnection`, `openContextMenu`;
- mode controllers: `crop`, `touchNavigation`.

The host interface is deliberately explicit. If a new pointer feature needs a new
field, it is added to `PointerHost` and documented; the controller does not receive
the whole `CanvasView` instance.

### I. Module growth policy

Extraction alone will not keep the system robust if new code keeps landing in the
same files. Add a policy and a blocking gate.

1. **Module-first rule.** New user-facing behaviour goes in
   `src/features/<feature>/`, `src/app/<controller>`, `src/canvas/<module>`,
   `src/model` or `src/io`. `App.ts`, `CanvasView.ts` and `itemRenderer.ts` may
   only wire, dispatch or expose a host API. A new method larger than roughly 40
   lines in an integration file needs either a module or an explicit justification
   in the PR.
2. **File budgets are blocking.** Add `file-budgets.json` and
   `scripts/check-file-budgets.mjs` and run it in CI:
   ```json
   {
     "defaultMax": 700,
     "directoryMax": {
       "src/canvas/items": 400,
       "src/canvas/pointer": 500
     },
     "files": {
       "src/app/App.ts": 1684,
       "src/canvas/CanvasView.ts": 3470,
       "src/canvas/itemRenderer.ts": 15
     }
   }
   ```
   New files default to 700 lines. A listed file may not grow above its recorded
   budget. Every extraction PR lowers the recorded number; a temporary increase is
   a separate, reviewed change with a follow-up issue. Generated files such as
   `src/i18n/types.generated.ts` are excluded.
3. **Ratchet after every extraction.** The budget commit is part of the same PR
   that shrinks the file, so the next change starts from the smaller number.
4. **Keep the existing boundary rule.** `@typescript-eslint/no-restricted-imports`
   still prevents features, model, IO and canvas helpers from importing `App.ts` or
   `CanvasView.ts`.
5. **Review checklist.** Add `Budget impact:` and “no new logic in an integration
   file” to `.github/pull_request_template.md`.
6. **ADR 0009.** Record the pointer host interface, the item renderer modules and
   the file-budget policy in one accepted ADR, linked from `AGENTS.md` and

`docs:capture` updates `docs/screenshots/manifest.json` and its source fingerprint.

fresh capture is expected and the manifest diff must be reviewed. Record the

shortcut or a user workflow needs either a documented reason or a revert.

## 6. Risks

| Risk | Mitigation |
| --- | --- |
| Refactor changes behaviour that no test covers | characterisation tests and manual desktop checklist first |
| CSS split changes the cascade | mechanical contiguous split, no reordering, media queries stay in place |
| `docs-fingerprint.mjs` breaks when `styles.css` is removed | update `ROOT_FILES`; `src/styles/**` is already scanned |
| Screenshots look stale after the split | run `docs:capture`, review the manifest and pixel diff |
| Large files regrow | blocking file budgets, module-first rule and PR template check |
| Pointer extraction changes event ordering or capture | one gesture family per PR, preserve listener order, `test:canvas` and `test:touch` after each |
| Item renderer split drifts visually | one item family per PR, `docs:capture` diff and `test:canvas` after each |
| Budget friction slows delivery | a temporary increase is a separate reviewed change with a follow-up issue; the next extraction ratchets it down |
| New code lands in an integration file | `Budget impact:` in the PR template, module-first review rule and the budget gate |
| Type-only imports fail the boundary rule | use `@typescript-eslint/no-restricted-imports` with `allowTypeImports`; document `splitView.ts` |
| Parallel work on the same files | merge order above; rebase before starting a seam |
| Over-refactoring | one seam per PR, no behaviour change, no new features |
| Theme scope creep | D2 is explicitly out of scope; only the token contract is prepared |
| Theme flashes at boot | external CSP-safe bootstrap script, native window background decision |
| Existing theme previews drift or are forgotten | reference `docs/theme-preview` in the plan and add `npm run theme:preview` |
| Playwright flakiness | keep scripts deterministic, publish failure artifacts |
| Desktop-only flows remain untested | document the manual checklist and extend the Tauri smoke where cheap |
