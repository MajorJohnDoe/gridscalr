# Known limitations


- The drawing PDF export bakes visible markups into page content as vectors and keeps that flattened output as the deterministic default. **Optional layers (OCG)** can additionally write visible project layers as standard PDF optional-content groups, but reader support varies and one group cannot express different visibility on different pages: switching a group off in a reader hides that layer on every exported page. One group per layer, rather than one per layer and page, is a deliberate choice: per-page groups would multiply the reader's layer list by the page count and could not express the layer hierarchy (F-023, ADR [0016](adr/0016-optional-content-export-shape.md)). Hidden layers, hidden ancestors and hidden items are never exported, and a layer whose content is not visible on any exported page is not written as an empty group.
- **Review annotations** are standard PDF annotation dictionaries for review in other readers. GridScalr attaches no appearance stream, so their appearance depends on the reader; their geometry is approximate, they are not an editable project, and they are never read back into GridScalr item data or quantities.
- Operation card sheets use built-in templates only. Custom frames, image logos, automatic page numbering and automatic equipment tags are not supported yet. The page field is free text and is not renumbered when sheets are added or removed.
- Template field values are stored in the project and exported as searchable PDF text, but the in-app search does not index them. Page thumbnails and the read-only reference pane show the static frame without field values.
- Data-summary sheets have a fixed fifteen-column layout and a paper-dependent number of 9 mm rows (about 23 on A3 and 36 on A2). Columns cannot be added, removed or reordered; extra rows require another data-summary sheet. Cells are single-line and shrink to fit.
- Changing a sheet's paper is structural and cannot be undone. Field values, including table cells in rows that no longer fit, are retained and reappear when the larger paper is selected again.
- Text notes placed with the Text tool do not wrap; use `Shift+Enter` for an explicit line break or the Text box tool for a fixed-width box that wraps automatically. Text boxes support formatting per selected range, and the inline editor shows bold, italic, underline, size and colour while typing. Only text boxes store runs; callouts, clouds and plain text notes keep one style per item. Text boxes are transparent unless **White background** is enabled.
- There is no cloud sync, collaboration, or automatic update service.
- Concurrent edits are protected by a conditional save. The desktop app compares the file it loaded with the file on disk immediately before the rename and offers **Save as conflicted copy** by default, or **Compare with disk version**, **Reload from disk**, **Overwrite** and **Cancel**. A conflict therefore preserves both versions. **Compare with disk version** compares project data, not source drawing bytes; it matches items by id, geometry and a move tolerance, so a heavily reworked item can appear as removed plus added, and it never merges or writes. A cloud client can still write to the file in the short window between the final hash check and the rename; that remains a limitation of any local compare-and-swap. The browser fallback downloads the project and cannot perform a conditional write.
- **File → Conflicted copies…** and the project status popover list the copies in the open project's folder only. A copy left behind by a renamed or moved project is not found automatically; open the old folder yourself. Discovery matches the documented name exactly and never follows a symbolic link, so a renamed copy is an ordinary file. There is no automatic cleanup, no retention limit and no automatic merge: a copy stays until you delete it, and a deleted copy is permanent. The copy list shows the file's time and size, not its content or project identity; use **Compare with open project** to see what differs. The browser fallback has no native folder access and therefore no conflicted-copy manager.
- The robustness gate (`npm run test:robustness`) proves the application-level invariants: page identity through seeded structural sequences, competing saves, schema 1–26 migration and source-storage behaviour. It cannot simulate every operating-system crash instruction, a real cloud client racing the final hash check and rename, external source truth without reading the drawing, or native file dialogs. Those remain manual review items or documented limitations above.
- A reference PDF on a shared or cloud-synced folder can be changed or moved by someone else. GridScalr detects it and offers Reload, Use current, Relink and Copy into project, but a reference does not protect the working geometry until you choose one of those actions. A managed copy protects against the original moving or changing; it does not protect against someone editing the copy. The copy's SHA-256 remains authoritative and a changed copy is reported.
- The cloud and network recommendation is a path-segment heuristic: UNC paths starting with `\\` and folders named OneDrive, Dropbox, Google Drive, iCloud, Box, SharePoint, Nextcloud, ownCloud, Seafile, pCloud, MEGA, Yandex Disk or Nutstore. It can miss a renamed folder or flag an unrelated one. It only recommends **Copy drawing into project**; the user always chooses and reference stays valid.
- The managed-copy folder is always the sibling `<project>.drawings/` next to the project file. It is not user-selectable. Renaming the project file does not rename an existing drawings folder; the relative links keep working, and **Consolidate drawings…** can recreate copies under the new name if needed.
- **File → Save a copy…** writes only the project file. Managed drawings stay in the original project's `<project>.drawings/` folder, so the copy links back to them. Use **File → Share project package…** when the copy must be self-contained.
- **File → Share project package…** writes a local `.gridscalr.zip` through the normal save dialog. There is no operating-system share sheet, email integration or upload; send the file yourself.
- Managed copies are not synchronised or deleted automatically. Removing a document or detaching it from its source leaves the copy on disk, **Consolidate drawings…** can leave unreferenced copies if a later copy fails, and **Replace source…** on a managed PDF copies the new revision into the project while the previous copy stays behind as an unreferenced file. The project file stays valid. **File → Project doctor…** lists every unreferenced copy in the project drawings folder and removes only the ones you select and confirm; a copy that is still referenced is never removed. Removal uses the operating system trash when available and otherwise moves the files into a timestamped `.removed` folder beside the project, so they are recoverable until you delete that folder yourself.
- The unused managed-copy listing reads only regular `.pdf` files directly inside `<project>.drawings/`, one level deep. A subfolder you create yourself, and any other file type, is never listed or offered for removal; the fixed flat folder is the only layout GridScalr writes.
- Replacing a managed source keeps managed mode for a PDF only. A TIF document carries its derived PDF inside the project, so a TIF replacement stays a reference and its original path is not copied into the drawings folder.
- Relink by checksum searches only the project folder and its `<project>.drawings/` folder, never the whole file system. A drawing outside those folders must be picked manually.
- The source-status poll hashes a PDF once per path, size and stored checksum. A change that keeps the same byte size between polls is only detected after the app restarts or the file is reloaded; reopening the project runs a full checksum check.
- Reload and Relink refuse a drawing whose page count changed and point to **Replace source…** instead. The page mapping is never guessed: the default is the same position, and a revision with reordered sheets must be remapped in the dialog.
- Drag-and-drop page reorder is enabled for every page, but the UI does not yet guide a cross-document reorder with a separate confirmation step. The data model supports it. Reordering and inserting pages are one undo step each; deleting and duplicating pages remain explicit structural actions that cannot be undone. The Pages-panel multi-selection drives reorder and **Move page to position…**, but duplicate and delete still act on the current page (F-080).
- Pages, Layers and Markups share focus, selection, filter and collapse conventions, but only Pages and Layers have a user-defined order. The Markups table is sorted and grouped, so it has no drag handle or drop line.
- Layers nest only inside their own kind. A drawing layer cannot become the parent of a measurement layer, and a layer cannot be nested inside its own subtree. Layer drag and keyboard movement stay inside one kind group. A filtered layer list keeps the layers it does not show in their existing slots; the search narrows what can be picked, not the saved order.
- Schema 26 stores an optional layer `parentId`, and the model resolves inherited visibility and locking, subtree deletion and page-delete cleanup. The Layers panel nests, renames and reorders the tree, bulk visibility and locking are enforced on the canvas, hit-testing, quantities and PDF export, and the optional-content export writes the visible hierarchy as nested headings. Grouping does not restack layers, so the **Move up** and **Move down** menu commands still act on the flat kind list rather than on sibling order; use the drag handle or `Alt` + arrows for tree order.
- Nested optional-content headings are written as `/Name` plus `/Order` dictionaries in `/OCProperties /D /Order`, which Acrobat and most desktop readers read. pdf.js, and therefore Firefox's built-in viewer, only reads the ISO array form of a named group, so it lists the same groups flat instead of nested (F-087). The groups themselves are present and toggleable in every reader. The interoperability defect is ours: the fix is to emit the ISO array form, decided in ADR [0016](adr/0016-optional-content-export-shape.md) and tracked as a separate issue because the array form makes the heading non-selectable and needs a name rule for a group that owns items, plus verification in Acrobat and Firefox.
- Markups view favourites (the star button) are stored locally per project and machine, not in the project file. Saved views, their filters and their order travel with the `.gridscalr` file; favourites do not (F-081).
- Form fields and embedded PDF annotations are not editable.
- Measurements use the active page's scale; a manual scale or reference calibration can be applied to all pages with the same drawing scale.
- Snapping targets markup endpoints, midpoints, intersections and I/O rail rows. Snapping directly to the PDF drawing's vector geometry is a separate future feature.
- Schematic pipes do not build a connectivity graph. There is no automatic cable routing, junction detection or I/O extraction; control cables snap to rail rows and connection dots are placed explicitly.
- The line-type editor renames, recolours, reweights, adds and removes project media classes. A line type sets the colour, width and dash when a run is created; editing or deleting a class later does not restyle existing runs, so old drawings remain stable. Line type names and colours are project data, not a shared company standard.
- **Outside drawing area** and its fit action apply to template sheets. The action scales down and centres unlocked, visible objects; locked objects are left in place. Drawings on imported PDF pages have no sheet drawing area to fit into.
- Rectangle and ellipse quick areas can be moved and reshaped from their two opposite points but cannot be rotated.
- Images support PNG and JPEG only. They are embedded in the project and count toward its file size; there is no external `assets/` folder. Image cropping, filters, and colour correction are not available.
- TIF import reads stripped and tiled scans with no compression, PackBits, LZW, Deflate, JPEG-in-TIFF, CCITT G3 or CCITT G4. Greyscale, RGB(A), YCbCr and CMYK images are supported at 1, 2, 4, 8 and 16 bits per sample, with the horizontal predictor at 8 and 16 bits. 16-bit samples are reduced to 8 bits (F-090) and RGBA alpha is composited over white (F-089), because a page is embedded as a flat PDF image and a PDF image has no alpha channel without a separate `/SMask`. A tiled page is composed into one band per tile row, with cropped edge tiles, so it imports at the same size and pixels as a stripped page. JPEG scans are embedded as their original JPEG stream (`/DCTDecode`, with a shared `JPEGTables` set joined to each strip) and are never re-encoded; a CMYK stream keeps the sample convention recorded by its Adobe marker, so a stream without a marker is not inverted and YCCK is rejected (F-095). Palette colour, JPEG 2000, tiled JPEG (F-093), tiled CCITT, per-strip old-style JPEG without a complete stream (F-094), horizontal differencing on 1-, 2- or 4-bit samples (F-092), YCCK colour, planar channel layouts, signed or floating-point samples, tile grids over 65 536 tiles, and pages that would need more than 256 MB of decoded image data are rejected with a message that names the reason; a rejected scan never produces a partial or black page. TIF pages can be deleted like any other page but cannot be rearranged, and closing a TIF drawing's original file has no effect because the converted PDF is embedded.
- A decoded colour or greyscale TIF page is the largest thing a project file can contain: its derived PDF is embedded as base64 in the `.gridscalr` JSON, so every save, autosave snapshot and undo snapshot carries those bytes. The accepted budget is 8 MiB of project JSON per 25-megapixel colour page and 160 MiB of embedded derived PDFs per project — twenty such sheets, or eight full A1 sheets at 300 DPI, which measure 20 MiB each (ADR [0015](adr/0015-colour-scan-storage.md)). A photographic or poorly compressible sheet can need up to about 100 MiB at 25 megapixels, and the 256 MiB decoded-raster guard allows a page that produces up to about 341 MiB of base64, which the 256 MB project limit then refuses. The budget is an operating limit, not a new refusal: split a large colour set into one project per building or floor. Above the 48-million-character history budget the undo history shrinks to four snapshots. Keeping the TIF as a reference and rebuilding a cached derived PDF needs schema 27 and is a separate follow-up issue.
- New sheets and imported pages append by default. A PDF or TIF dropped on the Pages panel is inserted at the drop line, uses the same page picker and import preflight, and is one undo step. A page can be deleted explicitly: its items and page state are removed and later pages keep their stable IDs. Page reorder and page insert are also one undo step each; deleting and duplicating a page remain explicit and cannot be undone. If a dropped drawing accepts the managed-copy recommendation, that copy is a later history boundary, so Undo does not remove the import; see F-076.
- Page status badges derive from project and source state only. **OCR missing** is shown for TIF pages, which are always scans; a scanned PDF page has no cheap way to prove that its text layer is empty, so it is not badged until OCR has run and stored a result. **Source changed** appears only after a completed source-file check, and reordering or dropping a drawing is disabled while a status filter hides pages.
- Import pages from another project appends pages unless an insertion position is chosen and creates one destination layer per source layer identity, shared across the imported pages. The source project is read-only. A preflight lists pages, items, references, unreadable files, skipped pages, checksum warnings and page-count changes before anything changes. Imported pages keep optional source-project and revision provenance; it is context, not a signature. The revision hash is computed from the raw project file bytes from 0.25.0 onward; pages imported by an older release keep their historical decoded-text hash and are not rewritten. Provenance stores the source project's stable ID, not its display name, so Properties and Markups show a shortened ID; adding the name needs a later additive field or schema change (F-083). Only plain `.gridscalr`/JSON files are supported; extract `.gridscalr.zip` packages first. Import previews show the page background, not the markups. Undo keeps the imported PDF proxies in memory until the project is closed or replaced, which makes redo immediate.
- Deleting a page does not remove empty page-scoped layers that were created there. Remove them from the Layers panel when they are no longer needed.
- Custom count types use one of the five built-in vector glyphs. Uploaded or custom-drawn count artwork is not supported. A count can represent several pieces with **Pieces per object**.
- Count schedules for doors, windows and fixtures group counts by type, category and room. They do not store width, height, fire rating or other door/window schedule attributes; that remains a separate future feature.
- Statutory Swedish area classifications such as BTA, BRA, NTA and LOA are not calculated. Categories and rooms are user-defined grouping labels, not a statutory area model.
- The 1.0 Windows and macOS builds are unsigned. Windows shows SmartScreen warnings and macOS requires the user to approve the app through System Settings → Privacy & Security. Verify published SHA-256 checksums before running a download.
- The full user guide and workflows are English-only in 1.0. The Swedish UI includes a Swedish quick start and an explicit English fallback for the full guides.
- The symbol library is built in and vector-only: 52 facility signs and 156 stroke-only schematic symbols. Custom symbol uploads and symbol quantities in the procurement report are not supported yet. Symbols can be resized by dragging a corner. Tags are free text and are never numbered automatically. The pictograms are original vector interpretations, not certified SS-EN ISO 7010 reproductions and not reproductions of SS-EN ISO 14617, IEC 60617 or any other named schematic standard.
- Quantity reports are available as CSV, XLSX and PDF. CSV defaults to the app locale (Swedish uses semicolons and decimal commas) and can switch to Interchange (RFC 4180) in Preferences. XLSX uses numeric cells and is unaffected.
- The reference pane is read-only and shares zoom and pan with the primary canvas. Its page can follow the primary page or be set independently, but there is no independent zoom, no second reference pane and no editing in the reference pane.
- Revision comparison compares measurement and markup data plus the rendered source pages. A raw PDF drawing reference has no markup data, so it supports side-by-side, overlay and a visual comparison PDF but no difference list. Neither mode performs a semantic diff of the PDF's raw vector operators.
- A revision comparison opens the reference project's source drawings as well as the project file. If those drawings have moved, the reference cannot be loaded until they are restored or the project is reopened from its original location.
- Radius, diameter and arc measurements are reported as **length** quantities; they do not create separate quantity types.
- Slope is measured from the two drawn points (rise over run). There is no elevation input for a slope between two real-world levels. Volume depth is entered in the project length unit, not measured from the drawing.
- OCR uses the bundled English (`eng`) and Swedish (`swe`) Tesseract models only. Other languages are not available, and OCR quality depends on scan resolution, contrast and skew.
- OCR runs on demand and can take several seconds per scanned page. The stored OCR index makes later searches fast, but re-running OCR replaces the page's stored words.
- While a project is open, source-file status checks that each drawing still exists and compares its byte size with the size recorded when it was linked. A change that keeps the same byte size is only detected by reopening the project or by the normal checksum check on open.
- Project saves replace the file with a single rename after flushing a temporary file. A folder or file system that cannot rename over an existing file, such as some read-only or network shares, refuses the save and keeps the previous project; save locally or use **File → Save a copy…**.
- Automatic rolling backups are stored in the local app data folder, keyed by project ID. They keep between 2 and 10 recent saves per project (default 3, set in **Preferences → Data**), are never added to recent files or packages, and are not uploaded or synced. Deleting them removes only the app-data copies; use **File → Save a copy…** when a portable backup is needed outside this computer.
- The project status popover reads the rolling backup list once when it opens, so a backup written while it is open appears on the next open. The last save time is the project file's modification time: a project opened from disk shows the previous save, and a browser-fallback download has no file time. A failed backup-list read is shown as no automatic backup rather than as a separate error, and the popover does not poll or refresh on a timer.
- A restored backup resolves relative drawing links from the project path recorded with that backup, then from the folder of the open project. A backup taken before the origin path was recorded still resolves through the open project's folder. A drawing that cannot be resolved is listed before the restore starts and must be located explicitly; GridScalr never substitutes the stale absolute path that the backup also carries. A backup restored on a computer without the drawings still needs each drawing located by hand, and a located drawing is stored as an absolute reference because its new relative link is unknown.
- Project packages are standard unencrypted ZIP files. GridScalr does not encrypt or cryptographically sign them; the manifest checksums detect corruption and accidental changes, not deliberate tampering. Each managed drawing is included once; a package is a transport copy and does not change the live reference or managed-copy mode.
- Original TIF scans and quantity/drawing exports are opt-in when packaging and are off by default. The TIF document's embedded PDF is enough to open and edit the project; the scan is only needed as source material.
- Packaging and open-package extraction require the desktop app. In the browser fallback the commands are visible but disabled with a desktop-only note. Packages can still be unzipped manually and the `.gridscalr` file opened with **File → Open project…** in the desktop app.
- Optional package exports are generated in memory before the ZIP is written. Very large drawing exports can take a while and need temporary memory, but the source PDFs themselves are streamed in Rust.
- A project file is limited to 256 MB and one opened source PDF/TIF to 1 GiB. A larger file fails with a localized message and the open project is left untouched; the browser fallback checks the picked file size before reading.
- A project package is limited to 2 GiB uncompressed, 1 GiB per entry and 2 GiB for the ZIP file itself, and one managed copy is limited by the same 1 GiB source cap as an opened drawing. The package dialog shows the expected uncompressed size before anything is written, package creation refuses a package over the 2 GiB limit or a destination without the size plus a 64 MiB reserve, and open-package extraction applies the same two checks. A large package still needs that free space temporarily because the previous extracted folder is kept until the new one is verified.
- A crashed save can leave a flushed temporary sibling next to the project, and a crashed package extraction can leave its staging folder beside the project. Opening a project removes both: only names that exactly match the app's generated patterns (`.<name>.<pid>.<stamp>.<counter>.tmp` or `.copy`, and `.<name>.extract-<pid>-<stamp>` folders), only entries older than ten minutes, and never an entry carrying the running process's own id. A `.<name>.previous-<pid>-<stamp>` folder from a replaced extraction is kept, because it holds the folder the user replaced, and a crashed save in a folder that is never opened again stays until the next save or open there.
- A project may reference a drawing outside its own folder. A dismissible warning names those drawings and offers **Copy into project** and **Relink**; the reference itself stays valid and is never rejected. Only open projects from a source you trust, because a project can point at any file you are allowed to read.
- Package extraction refuses unknown archive entries. Do not add extra files to a package ZIP unless you also update its manifest; manual unzip and opening the project is not affected.
- Recovery autosave needs local IndexedDB or, as a fallback, localStorage space. It keeps the latest snapshot per project plus one previous, and up to ten structural checkpoints per project, inside an explicit byte budget: **64 MiB per project and 256 MiB for the whole recovery store on this computer**. A write that would exceed either budget prunes the oldest records first, so the store cannot grow without limit and cannot exhaust the browser's IndexedDB quota before recovery matters. The newest autosave and the newest checkpoint of every project are never pruned by rotation: a project whose single snapshot is larger than 64 MiB keeps those two records and nothing else. The budget counts the serialized snapshot bytes; record metadata adds a few hundred bytes per record and is bounded by the twelve-record count limit. The recovery center shows the total and per-project size, diagnostics report the same totals without names or paths, and both `Help → Copy diagnostics` and the center list each record's size. When storage is still full, for example because another site uses the same quota, GridScalr names the file save and the recovery center as the next actions, and the **Recovery storage full** chip opens the center. The localStorage fallback has its own small quota (about 5 MB), so a large project falls back to that actionable message instead of keeping a partial snapshot. Pruning uses only the local store and never touches project files or drawings.
- The byte budget is not derived from `navigator.storage.estimate()`. On an origin with a very small quota the store can still hit the browser limit before 256 MiB, and the quota-failure message remains the fallback.
- A record written before the byte budget existed has no stored snapshot size; the recovery center measures it once from the serialized string when it is listed. New records persist the size at write time.
- Autosave is an app-level preference, not a per-project setting. It is on by default and writes at most one snapshot every 15, 30 or 60 seconds after a change. Turning it off or pausing it for the session stops periodic snapshots immediately, so an app crash loses every edit since the last manual save or structural checkpoint. Checkpoints before page, source and import operations are still written while autosave is off or paused. A pause resets when GridScalr starts again.
- The sidecar project lock (`<project>.gridscalr.lock`) is advisory, not a guarantee. It warns when another live instance has the project open and defaults to view-only, but a cloud client or a sleeping laptop can delay the heartbeat. A crash can leave a stale lock for up to five minutes; a stale or corrupt lock never blocks opening and can be cleared explicitly. The conditional save remains the actual protection.
- A view-only session disables every project mutation. Pan, zoom, search, the reference pane, export, package and **Save a copy…** still work; a normal Save and Save As are refused. Running OCR is disabled because it stores a page index in the project; text already indexed remains searchable. **Take over to edit** re-checks the lock before editing is enabled. The original project file is not written from a view-only session.
- The integrity validator proves internal referential consistency, not external truth. The project doctor reports source availability separately, so a missing or changed drawing is a warning with relink and copy actions, never a save error. The validator still cannot confirm that a referenced drawing is the correct revision, that a PDF still matches its checksum without reading it, or that quantities and measurements are commercially correct.
- Explicit repairs cover duplicate IDs, dangling references and stale OCR. The doctor can apply them as one selection or as a subset, and the preview is generated from the same plan that is applied, so the listed renames and removals match the saved repaired copy. Other problems are reported but not rewritten automatically, including image assets whose MIME and data disagree, invalid image or text-box geometry, dangling report metadata and invalid optional provenance. A repair that would change nothing is not applied. Unreferenced managed drawings are handled by the doctor's explicit cleanup, not by a repair. Review the remaining issues manually or save a repaired copy only after they are acceptable.
- The doctor's preview lists at most 20 concrete changes for a large repair, and diagnostics export lists issue codes and counts rather than the full planned rename set. A very large duplicate-ID repair must therefore be reviewed in the saved copy, not only in the preview.
- Duplicate-ID repair keeps the first occurrence of an ID and renames later ones. References that used the duplicated ID cannot be attributed to a specific occurrence and remain attached to the first one. Review affected pages and markups before relying on the repaired copy.
- A load report and the project doctor use stable technical codes for dropped or repaired load entries. They describe what normalization did; they do not recover data that was never valid.
- The sidecar lock, file watcher, view-only enforcement and explicit take-over are desktop-only. The browser fallback keeps the scoped IndexedDB recovery store and downloads on Save; it has no lock file or disk-change banner.
- The desktop window draws its own title row on Windows and Linux, so the Windows 11 snap-layout flyout on hover over the maximize button is not shown. Aero snap by dragging the window to a screen edge, double-click to maximize and the system menu still work. macOS keeps the native traffic lights and title bar behaviour.
- File associations are registered by the installers only. The portable `gridscalr.exe` and the AppImage do not claim `.gridscalr`, and Linux associations depend on the desktop environment reading the installed `.desktop` file. GridScalr never claims `.pdf`.
- The AppImage does not yet pass the opened file, because Tauri's AppImage desktop entry omits the `%f` argument ([tauri-apps/tauri#16014](https://github.com/tauri-apps/tauri/issues/16014)). The `.deb` and `.rpm` packages ship a custom desktop entry and do pass it.
- Single instance uses a per-user channel (D-Bus on Linux). In a session without a session bus, or when the app is started from two different user accounts, a second launch starts a second window instead of focusing the first.
- The remembered window position is only restored when it still intersects a connected monitor; otherwise the operating system places the window. Window geometry is stored per user account and is not part of the project file.
- The packaged smoke test drives the app from inside: it covers launch, opening the demo, saving, reopening and the unsaved-changes prompt. Native file dialogs, menu clicks and drag-and-drop are not automated on any platform, and macOS has no WebDriver (`tauri-driver`) support at all; those paths stay in the manual install checklist.
- The demo project is copied to the app data folder on first use, and edits are saved to that copy rather than to the bundled fixture. Delete the `demo` folder under the app data directory (for example `%APPDATA%\com.gridscalr.desktop\demo` on Windows or `~/.local/share/com.gridscalr.desktop/demo` on Linux) to restore the bundled version. The demo is not available in the browser fallback.
- The language selector covers the interface, reports and export headings. A low-level filesystem failure shows a localized message and keeps the operating system's technical detail as a separate line.
- The static boot fallback in `index.html` is English until the selected catalog loads; it is replaced before the app starts, and startup failures after that point use the active language.
- Diagnostics and the local event log are stored on the computer only. There is no telemetry, crash reporting or upload, and the log keeps the last 80 entries with paths, drawing names and labels removed. Startup failures before the log is available are shown on the boot screen instead.
- The Linux GTK stack currently resolves `glib 0.18.5`, which has a medium-severity soundness advisory fixed in `glib 0.20.0`. GridScalr cannot upgrade it independently because Tauri's GTK 0.18 dependencies pin that generation. The Windows artifacts do not use this code path; the dependency gate accepts it with a written reason and a quarterly review until a future Tauri/GTK upgrade. Tracked in [#21](https://github.com/MajorJohnDoe/gridscalr/issues/21).

## Large-project performance

The **reference project** is generated deterministically by
`npm run bench:large` from the demo takeoff: 150 pages, 15,000 markup items,
60 embedded images and a serialized project around 8 MB. Source PDF bytes are
not duplicated in the benchmark; the Rust package tests exercise the streaming
1 GB path separately. Override the shape with `GRIDSCALR_BENCH_PAGES`,
`GRIDSCALR_BENCH_ITEMS` and `GRIDSCALR_BENCH_IMAGES`.

The budgets below are measured on the development machine with Chromium 1248,
Node 24 and the browser fallback. Run the benchmark on each release platform
before a release candidate; a regression beyond a budget blocks the release.

| Measure | Budget | Notes |
| --- | --- | --- |
| p95 edit latency | under 100 ms | A single history-tracked mutation in the reference project. |
| Project open | under 10 s | Parsing and store setup; PDF rendering is separate and progressive. |
| Autosave | under 2 s | Debounce plus the IndexedDB recovery write. |
| Page switch | under 100 ms | Store page change without waiting for a render. |
| Memory | under 2 GB | Desktop app working set while the reference project is open. |
| UI freeze | under 2 s | Longer operations need progress and cancel. |

Undo history is adaptive: it keeps up to 80 snapshots for small projects and
shrinks towards four snapshots when a single serialized snapshot exceeds the
48-million-character budget. A very large project therefore keeps a shorter
undo history rather than exhausting memory.

The Markups table renders only the rows near its viewport, canvas rendering
skips items outside the visible viewport, and autosave stores one serialized
snapshot with a skip when nothing changed since the previous write. These are
the tested 1.0 limits; there is no promise of unlimited project size.
