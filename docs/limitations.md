# Known limitations


- The drawing PDF export bakes visible markups into page content as vectors and keeps that flattened output as the deterministic default. **Optional layers (OCG)** can additionally write visible project layers as standard PDF optional-content groups, but reader support varies and one group cannot express different visibility on different pages: switching a group off in a reader hides that layer on every exported page. One group per layer, rather than one per layer and page, is a deliberate choice: per-page groups would multiply the reader's layer list by the page count and could not express the layer hierarchy (F-023, ADR [0016](adr/0016-optional-content-export-shape.md)). Hidden layers, hidden ancestors and hidden items are never exported, and a layer whose content is not visible on any exported page is not written as an empty group.
- **Review annotations** are standard PDF annotation dictionaries for review in other readers. GridScalr attaches no appearance stream, so their appearance depends on the reader; their geometry is approximate, they are not an editable project, and they are never read back into GridScalr item data or quantities.
- Operation card sheets use built-in templates only. Custom frames, image logos, automatic page numbering and automatic equipment tags are not supported yet. The page field is free text and is not renumbered when sheets are added or removed.
- Template field values are stored in the project and exported as searchable PDF text, but the in-app search does not index them. Page thumbnails and the read-only reference pane show the static frame without field values.
- Data-summary sheets have a fixed fifteen-column layout and a paper-dependent number of 9 mm rows (about 23 on A3 and 36 on A2). Columns cannot be added, removed or reordered; extra rows require another data-summary sheet. Cells are single-line and shrink to fit.
- Changing a sheet's paper is structural and cannot be undone. Field values, including table cells in rows that no longer fit, are retained and reappear when the larger paper is selected again.
- Text notes placed with the Text tool do not wrap; use `Shift+Enter` for an explicit line break or the Text box tool for a fixed-width box that wraps automatically. Text boxes support formatting per selected range, and the inline editor shows bold, italic, underline, size and colour while typing. Only text boxes store runs; callouts, clouds and plain text notes keep one style per item. Text boxes are transparent unless **White background** is enabled.
- There is no cloud sync, collaboration, or automatic update service.
- Concurrent edits are protected by a conditional save. The desktop app compares the file it loaded with the file on disk immediately before the rename and offers **Save as conflicted copy** by default, or **Compare with disk version**, **Reload from disk**, **Overwrite** and **Cancel**. A conflict therefore preserves both versions. **Compare with disk version** compares project data, not source drawing bytes; it matches items by id, geometry and a move tolerance, so a heavily reworked item can appear as removed plus added, and it never merges or writes. A cloud client can still write to the file in the short window between the final hash check and the rename; that remains a limitation of any local compare-and-swap. The browser fallback downloads the project and cannot perform a conditional write.
- **File → Maintenance → Conflicted copies…** and the project status popover list the copies in the open project's folder only. A copy left behind by a renamed or moved project is not found automatically; open the old folder yourself. Discovery matches the documented name exactly and never follows a symbolic link, so a renamed copy is an ordinary file. There is no automatic cleanup, no retention limit and no automatic merge: a copy stays until you delete it, and a deleted copy is permanent. The copy list shows the file's time and size, not its content or project identity; use **Compare with open project** to see what differs. The browser fallback has no native folder access and therefore no conflicted-copy manager.
- The robustness gate (`npm run test:robustness`) proves the application-level invariants: page identity through seeded structural sequences, competing saves, schema 1–28 migration and source-storage behaviour. It cannot simulate every operating-system crash instruction, a real cloud client racing the final hash check and rename, external source truth without reading the drawing, or native file dialogs. Those remain manual review items or documented limitations above.
- A reference PDF on a shared or cloud-synced folder can be changed or moved by someone else. GridScalr detects it and offers Reload, Use current, Relink and Copy into project, but a reference does not protect the working geometry until you choose one of those actions. A managed copy protects against the original moving or changing; it does not protect against someone editing the copy. The copy's SHA-256 remains authoritative and a changed copy is reported.
- The cloud and network recommendation is a path-segment heuristic: UNC paths starting with `\\` and folders named OneDrive, Dropbox, Google Drive, iCloud, Box, SharePoint, Nextcloud, ownCloud, Seafile, pCloud, MEGA, Yandex Disk or Nutstore. It can miss a renamed folder or flag an unrelated one. It only recommends **Copy drawing into project**; the user always chooses and reference stays valid.
- The managed-copy folder is always the sibling `<project>.drawings/` next to the project file. It is not user-selectable. Renaming the project file does not rename an existing drawings folder; the relative links keep working, and **Consolidate drawings…** can recreate copies under the new name if needed.
- The derived-PDF cache folder is always the sibling `<project>.derived/` next to the project file, with the file name `<scan hash prefix>-v<converter version>-p<page count>.pdf`. It is not user-selectable. Renaming the project file does not rename an existing cache folder: a marker that no longer resolves is rebuilt from the reachable scan, and a scan that is also gone shows the one **Locate the scan…** path. A cache is never deleted automatically, so a stale cache for a replaced scan stays on disk as an unreferenced file; the project doctor reports a stale or invalid marker but does not remove the file. Deleting the folder by hand costs a rebuild, never page content.
- **File → Save a copy…** writes only the project file. Managed drawings stay in the original project's `<project>.drawings/` folder, so the copy links back to them, and a TIF cache marker still points at the original project's `<project>.derived/` folder: the copy rebuilds from the original scan when that scan is reachable, and otherwise asks for the scan. Use **File → Send & share → Share project package…** when the copy must be self-contained (the package includes either the cache or the original scan).
- **File → Send & share → Share project package…** writes a local `.gridscalr.zip` through the normal save dialog. There is no operating-system share sheet or upload; send the file yourself.
- **File → Send & share → Send by e-mail…** opens a new, unsent draft in a local mail client with the drawing PDF attached. It is desktop-only: webmail in a browser is not supported, because a `mailto:` link cannot carry an attachment. The PDF is written to the app cache folder `mail-outbox/`, which keeps the ten most recent attachments and deletes older ones at the next launch or export. Windows prefers Simple MAPI and falls back to `outlook.exe /a`; macOS drives Mail.app through `osascript`, which may ask for Automation permission the first time; Linux prefers `xdg-email --attach` and falls back to Thunderbird. The client may still show its own profile, security or attachment prompt, and closing the draft without sending is the client's choice, not an app failure. Nothing is sent automatically and the project file is never attached.
- Managed copies are not synchronised or deleted automatically. Removing a document or detaching it from its source leaves the copy on disk, **Consolidate drawings…** can leave unreferenced copies if a later copy fails, and **Replace source…** on a managed PDF copies the new revision into the project while the previous copy stays behind as an unreferenced file. The project file stays valid. **File → Maintenance → Project doctor…** lists every unreferenced copy in the project drawings folder and removes only the ones you select and confirm; a copy that is still referenced is never removed. Removal uses the operating system trash when available and otherwise moves the files into a timestamped `.removed` folder beside the project, so they are recoverable until you delete that folder yourself.
- The unused managed-copy listing reads only regular `.pdf` files directly inside `<project>.drawings/`, one level deep. A subfolder you create yourself, and any other file type, is never listed or offered for removal; the fixed flat folder is the only layout GridScalr writes.
- Replacing a managed source keeps managed mode for a PDF only. A TIF document's derived PDF is a cache artifact beside the project, not a managed copy, so a TIF replacement stays a reference and its original path is not copied into the drawings folder.
- Relink by checksum searches only the project folder and its `<project>.drawings/` folder, never the whole file system. A drawing outside those folders must be picked manually.
- The source-status poll hashes a PDF once per path, size and stored checksum. A change that keeps the same byte size between polls is only detected after the app restarts or the file is reloaded; reopening the project runs a full checksum check.
- Reload and Relink refuse a drawing whose page count changed and point to **Replace source…** instead. The page mapping is never guessed: the default is the same position, and a revision with reordered sheets must be remapped in the dialog.
- Drag-and-drop page reorder is enabled for every page, but the UI does not yet guide a cross-document reorder with a separate confirmation step. The data model supports it. Reordering and inserting pages are one undo step each; deleting and duplicating pages remain explicit structural actions that cannot be undone. The Pages-panel multi-selection drives reorder and **Move page to position…**, but duplicate and delete still act on the current page (F-080).
- Pages, Layers and Markups share focus, selection, filter and collapse conventions, but only Pages and Layers have a user-defined order. The Markups table is sorted and grouped, so it has no drag handle or drop line.
- Row reordering in the Pages list, the Layers tree and the takeoff table builder is a pointer gesture owned by the app, not an HTML5 drag. It therefore keeps working while the desktop window handles operating-system file drops, which is the state on Windows. The gesture is mouse or pen only: a finger scrolls the list, so touch reordering uses `Alt` + arrows, the layer `Alt` + `ArrowRight` / `ArrowLeft` nesting keys, or the takeoff builder's move buttons. A move must be released inside the list; releasing over the canvas or outside the window cancels it, and a press on a row control such as a colour swatch or an eye button keeps that control's own action.
- Layers nest only inside their own kind. A drawing layer cannot become the parent of a measurement layer, and a layer cannot be nested inside its own subtree. Layer drag and keyboard movement stay inside one kind group. A filtered layer list keeps the layers it does not show in their existing slots; the search narrows what can be picked, not the saved order.
- Schema 26 stores an optional layer `parentId`, and the model resolves inherited visibility and locking, subtree deletion and page-delete cleanup. The Layers panel nests, renames and reorders the tree, bulk visibility and locking are enforced on the canvas, hit-testing, quantities and PDF export, and the optional-content export writes the visible hierarchy as nested folders. Grouping does not restack layers, so the **Move up** and **Move down** menu commands still act on the flat kind list rather than on sibling order; use the drag handle or `Alt` + arrows for tree order.
- Schema 28 stores custom field definitions and field sets, spaces, schedules, schedule placements and summary settings, and the project doctor validates them. The field editor, the Properties **Fields** section, the space register, the takeoff table builder, the Takeoff tab and placed-table rendering shipped with Drift Slice 1. A placed table is drawn from the takeoff table definition at render time and is exported as vector text and lines in the drawing PDF. The takeoff table CSV round-trip shipped on schema 28; XLSX export and CSV import for other project data remain absent. Takeoff table definitions created in the Takeoff tab are live views; nothing is stored except the definition and each placement's box and row range. 1.0 remains deferred.
- Custom fields are editable for the **measurement** and **space** scopes; a space value is filled in the space form in **View → Spaces…**. The other scopes (`asset`, `issue`, `inspection`, `document`) have no entity in schema 28, so the editor offers Measurement and Space only. A field set fills measurement defaults; applying a set to a space is not part of this slice.
- The empty field editor explains what a field is but offers no template, so the first field still requires inventing a key and a type. A named template would be a product decision about which fields are standard and how their labels follow the interface language (F-119).
- The space register is a dialog opened from **View → Spaces…** (`Ctrl+Alt+R`), not a dock panel. It lists every space in one tree; there is no paging, filtering or search yet. The dialog is non-modal and rebuilds when the drawing selection or project data changes, so an area measurement can be selected while the register stays open (F-121).
- A space area is always reported in m², independent of the project area unit chosen for measurements, because the register is a room register rather than a measurement readout. A linked area measurement contributes its own page scale, so a scale-locked page and the page scale can both make the reported area change.
- A linked measurement without a page scale makes the whole space area missing instead of a partial sum. The row reports why. Hidden measurements and hidden layers are excluded from the sum, while locked measurements are included, which is the same rule the quantity report and exports use.
- Creating rooms from the room text always creates root-level rooms. Moving them under a building or floor is a separate explicit step, and the action never links a measurement. Room text is read from every measurement, including hidden ones.
- A space with child spaces cannot be deleted: the delete is refused and names the child count, because silently reparenting a subtree is never done. Delete or move the children first. Deleting a space clears its measurement links but never deletes a measurement. The register has no bulk move and no subtree delete, so reorganising a flat register is a row-by-row job (F-122).
- Project page import does not merge or remap the space, schedule or field registers: an imported item can keep a `spaceId`, `scheduleId` or custom value that resolves only in the source project (F-118). The preflight names the counts before the commit. **Clear unresolved links**, off by default, clears a dangling room link, removes a placement whose schedule is missing and drops custom values without a destination field; the source project and source file are never changed. With the option off the copies keep their references and the validator and project doctor report them. Merging or remapping the registers remains an open product decision for a later import phase.
- Spaces have a takeoff table source in the Takeoff tab, can be placed on a drawing and are included in the takeoff table CSV round-trip. A space row is updated by its stable ID and is never created from CSV.
- The Takeoff tab lives in the right dock and reads the project live. **New takeoff table…** creates a definition with columns, filters, grouping, sorting and totals; only the definition is stored, so a moved, hidden or deleted measurement immediately changes the table. The tab inherits the 250–420 px right-dock width, so a takeoff table with more than about five columns scrolls sideways; there is no pop-out or full-width takeoff dock yet (F-125).
- The Takeoff tab never creates a takeoff table on open and never marks the project dirty for reading it. A project with no table shows the labelled **Preview – cannot be placed** state until **Create takeoff table** or **Create takeoff table and place…** is chosen. The standard table has fixed **Object**, **Count**, **Unit** and **Value** columns, one row per item and no filters; rename it or change its rules in the builder like any other table.
- One takeoff table reads one source: measurements or spaces. A single table cannot mix both, and there is no joined or cross-source table.
- Only the four cards **Rooms**, **Area**, **Walls** and **Doors** exist. A stored `summaryRole` that no card uses (floor, ceiling, roof or other) stays in the project but is not exposed in **Takeoff settings → Cards**, and no custom card can be defined yet.
- The right-dock live takeoff table stays a chrome table using the shell surface tokens, while a placed drawing table uses the `--table-*` document roles. On canvas those roles resolve from the active theme's tokens with the document values as fallback; the drawing PDF is fixed to the document palette. A white-paper banded sheet inside the dark dock would fight the surrounding controls and hover states; the dock is a live view, not a printed sheet. The quantity report reuses the printed palette for ink, rules and the header band, keeps its page on the PDF's default white rather than a palette paper token, and keeps the order-quantity accent and the clamped-deduction warning as report-only semantic colours (F-140).
- The panel rebuilds its toolbar with the shell. Focus is restored to the picker, chip or action that had it, so a keyboard user can change several filters or close the hub and builder dialogs without starting over. The table and the rest of the toolbar are still rebuilt from state, not patched (F-127).
- A card reads `summaryRole` and never a name. A missing source shows 0 with a **Configure** action; **Takeoff settings → Cards → Fed by** sets the source on categories and count types. Nothing is inferred on migration, so an existing project keeps zero Walls and Doors until a source is set.
- Card visibility follows the project's card settings, which default to all four visible. **Takeoff settings → Cards** switches each card on or off as one undo step.
- The **Walls** card sums visible length-family measurements whose category role is Wall. A measurement without a page scale is excluded and named in the card note. The **Doors** card sums pieces per object for count items whose count type role is Door. The **Area** card sums the derived area of rooms only; a room without a usable area is named and not counted as zero.
- The built-in preview groups visible measurements by category. It reports the item count, length, net area (deductions subtract) and the unit of the row, and totals length and area. It is not an order: waste, rounding and order quantities remain in **Order**.
- A schedule total is computed from the filtered rows. **Count** is a row count, not a sum of values. A sum that mixes units is marked **Mixed units** instead of presenting a comparable number. A deduction area contributes a negative value.
- `rowMode = "grouped"` shows one row per group with subtotals and exports read-only as CSV; `rowMode = "items"` is the round-trip mode. Grouping and totals are never stored.
- A schedule that references an unknown field, a deleted page, category, count type or space keeps the reference visible in the builder as **Unknown field** or an invalid filter, and the panel reports it. It never crashes and never silently drops the row. The project doctor validates the same references. Deleting a page removes it from every schedule page filter and reports the count, the same way a space, category or count type delete cleans the matching filter list. A schedule reference to a deleted custom field is not removed: the column or filter stays visible as **Unknown field** until it is repaired in the builder, and the project doctor reports it (F-123).
- A filter that does not apply to the space source (category, count type, item kind) is named as inapplicable and ignored rather than silently emptying the table.
- Deleting a schedule that a placed table references asks first, names the placement count and removes the schedule together with every placement in one undo step. The same cascade does not run when a project is edited by hand outside the app: a placement whose schedule is gone is drawn as a placeholder and reported by the project doctor.
- Hidden items and hidden layers never appear in a schedule or a KPI card; locked items do. A schedule row reveals its measurement, and a space row reveals the first visible linked measurement or the space's page.
- The takeoff performance targets from the plan are measured by `tests/schedulesPerformance.test.ts` on a 15 000-item synthetic project: the cold takeoff summary computes in about 17–20 ms (target 100 ms) and a cold 10 000-row schedule with grouping, sorting and a total in about 192–195 ms (target 250 ms) on the development container. A cached read is effectively free, and the cache is keyed by the project revision and the active locale. A placed table lays out its visible window in about 2 ms even when the source has 10 000 rows, because it draws only the row range that fits. The test asserts a looser hard ceiling so a slow CI runner records a regression instead of a flaky failure; `GRIDSCALR_PERF_STRICT=1` asserts the documented targets. A 1 000-row schedule renders through a bounded row window (about 26 rows plus overscan).
- Custom values appear in the Properties **Fields** section, as schedule columns through the stable `custom:<fieldId>` reference, in a placed table and its PDF export, and in the schedule CSV round-trip. They are not columns in the Markups table, the quantity report or the quantity CSV/XLSX reports, so a quantity report cannot show custom data yet.
- A placed schedule table is bounded by its box and row range. There is no automatic multi-page table, no repeated header across pages and no column that grows beyond the box: each cell is a single ellipsized line, the font never shrinks below 4.5 pt, and rows that still do not fit are reported as an overflow with **Continue on a new table** instead of being clipped. The continuation is a second placement with the same width and columns; reflowing the first table does not move it (F-128).
- The row range counts data rows, not group or subtotal rows. A grouped takeoff table shows one row per group with its subtotal, and the grand total always covers the whole filtered set rather than only the visible range. A group subtotal also covers its whole group even when a row range shows only part of it. A total that mixes units stays marked, as in the Takeoff tab.
- Canvas text is measured with the browser font and PDF text with the embedded Liberation font, so an ellipsized cell can break at a slightly different character between screen and export. The columns, rows, subtotals, totals and overflow are otherwise computed by one shared layout function. The inspector's overflow warning uses the canvas metric, so a cell exactly at the boundary can be reported as fitting on screen and overflowing in the export, or the reverse (F-129).
- A placed table height does not grow when its row range grows. Drag a corner to make room, or use **Change row range…** and **Continue on a new table**. The default position is near the top-left of the page; nothing prevents a placement from being moved over drawing content.
- Schedule CSV import updates existing rows only. A row added in Excel has an unknown ID and is rejected; it never creates a measurement or space (F-132). It also cannot change reference or derived columns such as page, layer, category, space, count type, item status, value, unit, area or timestamps, because the CSV shows their display labels rather than stable references (F-130). Those columns are listed as read-only in the dry run and are left untouched. XLSX is not an import or a schedule export format; the Markups and quantity CSV files are not round-trip formats either.
- A schedule CSV export is bounded to one file, UTF-8, 10 MB and 20 000 data rows. The byte limit is checked before decoding and the row limit before any value is mapped; an over-limit file is refused with a message and nothing is applied. A CSV cell is never executed as a formula and is never rendered as HTML. Text that starts with `=`, `+`, `-`, `@`, a tab or a carriage return is exported with a leading apostrophe and that exact guard is removed on import.
- A grouped schedule exports one row per group with `Typ` = `group` and cannot be imported. Only a one-row-per-item schedule is a round-trip. The import matches a header by its bracketed key first and its label second, so a renamed column label or a switched interface language does not mis-map a value.
- A multi-choice custom value is exported as option labels separated by semicolons, because the table's comma-separated form would collide with the English delimiter. Import matches each token to an exact option id or an unambiguous exact label. A renamed option label therefore makes an older CSV report an invalid value rather than silently choosing another option (F-131). A yes/no field accepts `true`/`false`, `yes`/`no`, `ja`/`nej`, `1`/`0`; a decimal comma is accepted only when the file's delimiter is not a comma.
- The 10 000-row CSV budget is measured by `tests/schedulesCsvPerformance.test.ts`: on the development container an unchanged round trip exports in about 210 ms and plans the import in about 190 ms for 10 000 items and five columns. The test asserts a looser hard ceiling for CI and the documented 1 500 ms target under `GRIDSCALR_PERF_STRICT=1`.
- Custom values are explicit and typed. There are no formulas, calculated fields, inheritance, cross-field rules or defaults applied automatically on creation. A field set fills each member's default value once when you apply it to a measurement; it does not bind the measurement to the set, and it never overwrites a value that is already set.
- A field's `key` and `scope` are permanent after creation. A `type` change is blocked while any value exists, and an enum option that a value uses cannot be removed; add a new field or clear the values first. Labels, descriptions, option labels, validation limits, required and applies-to can change freely.
- Deleting a field removes its values from every measurement and space in the same undo step, and removes it from any field set. Undo restores all of it; a save after the deletion is final. Deleting a field set never deletes fields or values.
- Field definitions are capped at 500 per project, a text value at 2,000 characters unless the field sets a lower `maxLength`, a label at 120 characters, a description at 500 characters and a unit at 40 characters. Date values are stored as the text the date input produces (`YYYY-MM-DD`); a loaded date-time string is shown by its date part and is rewritten as a date when edited.
- Opening the field editor from **Takeoff settings → Fields** stacks it over the hub. Closing the editor returns to the Fields tab and repaints the hub in place; field edits update the inspector behind the dialog (F-120, ADR [0017](adr/0017-movable-non-modal-dialogs.md)).
- A field with `appliesTo` categories or count types is hidden when the selected measurement has no such category or count type. This is intentional: a restricted field never falls back to "applies" just because the attribute is missing.
- Nested optional-content folders are written in the ISO 32000-1 array form (`[ (Folder) 12 0 R [ (Child) 13 0 R ] ]`), the standard form; Firefox's pdf.js engine nests a group under its folder instead of listing it flat, and the serialized shape is asserted at every depth. Verification in Adobe Acrobat and PDF-XChange is still pending in [#257](https://github.com/MajorJohnDoe/gridscalr/issues/257), so the nesting is not yet claimed for those two readers. A folder label has no toggle of its own, so a group layer that also holds items shows the folder label plus a selectable entry with the same layer name; that entry toggles only the group's own items, while its child layers keep their own entries (F-087, ADR [0016](adr/0016-optional-content-export-shape.md)). Exports written before 0.28.0 used the Acrobat heading-dictionary form and still list their groups flat in Firefox; they are released files, not project data, and are not rewritten.
- Markups view favourites (the star button) are stored locally per project and machine, not in the project file. Saved views, their filters and their order travel with the `.gridscalr` file; favourites do not (F-081).
- Form fields and embedded PDF annotations are not editable.
- Measurements use the active page's scale; a manual scale or reference calibration can be applied to all pages with the same drawing scale.
- Snapping targets markup endpoints, midpoints, intersections and I/O rail rows. Snapping directly to the PDF drawing's vector geometry is a separate future feature.
- Schematic pipes do not build a connectivity graph. There is no automatic cable routing, junction detection or I/O extraction; control cables snap to rail rows and connection dots are placed explicitly.
- The line-type editor renames, recolours, reweights, adds and removes project media classes. A line type sets the colour, width and dash when a run is created; editing or deleting a class later does not restyle existing runs, so old drawings remain stable. Line type names and colours are project data, not a shared company standard.
- **Outside drawing area** and its fit action apply to template sheets. The action scales down and centres unlocked, visible objects; locked objects are left in place. Drawings on imported PDF pages have no sheet drawing area to fit into.
- Rectangle and ellipse quick areas can be moved and reshaped from their two opposite points but cannot be rotated.
- Images support PNG and JPEG only. They are embedded in the project and count toward its file size; there is no external `assets/` folder. Image cropping, filters, and colour correction are not available.
- TIF import reads stripped and tiled scans with no compression, PackBits, LZW, Deflate, JPEG-in-TIFF, CCITT G3 or CCITT G4. Greyscale, RGB(A), YCbCr and CMYK images are supported at 1, 2, 4, 8 and 16 bits per sample, with the horizontal predictor at 8 and 16 bits. 16-bit samples are reduced to 8 bits (F-090) and RGBA alpha is composited over white (F-089), because a page is embedded as a flat PDF image and a PDF image has no alpha channel without a separate `/SMask`. A tiled page is composed into one band per tile row, with cropped edge tiles, so it imports at the same size and pixels as a stripped page. JPEG scans are embedded as their original JPEG stream (`/DCTDecode`, with a shared `JPEGTables` set joined to each strip) and are never re-encoded; a CMYK stream keeps the sample convention recorded by its Adobe marker, so a stream without a marker is not inverted and YCCK is rejected (F-095). Palette colour, JPEG 2000, tiled JPEG (F-093), tiled CCITT, per-strip old-style JPEG without a complete stream (F-094), horizontal differencing on 1-, 2- or 4-bit samples (F-092), YCCK colour, planar channel layouts, signed or floating-point samples, tile grids over 65 536 tiles, and pages that would need more than 256 MB of decoded image data are rejected with a message that names the reason; a rejected scan never produces a partial or black page. TIF pages can be deleted and reordered like any other page, and closing a TIF drawing's original file has no effect because the converted PDF is embedded.
- A decoded colour or greyscale TIF page is the largest thing a project can contain, and schema 27 keeps it out of the project JSON. The derived PDF is a rebuildable cache in the sibling folder `<project>.derived/`, named by the scan's SHA-256, the converter version and the page count; the `.gridscalr` file carries only a `derivedPdf` marker. A measured reference project of six A2-class colour sheets (4960 × 3508 px at 300 DPI) serializes to 79.19 MiB with embedded bytes and 0.01 MiB with the cache, while the cache occupies 59.39 MiB on disk once (`GRIDSCALR_DERIVED_BENCH=1 npx vitest run tests/derivedPdfBudget.test.ts`). The enforced budget is **160 MiB of derived cache per project** — twenty 25-megapixel sheets, or eight full A1 sheets at 300 DPI — and the app warns once per changed state when the cache or the combined JSON plus cache reaches it. The only hard stop remains the 256 MB project limit; a save that fits it is never refused and no page is ever dropped to meet the budget. Split a large colour set into one project per building or floor. Above the 48-million-character history budget the undo history shrinks to four snapshots. See ADR [0015](adr/0015-colour-scan-storage.md).
- New sheets and imported pages append by default. A PDF or TIF dropped on the Pages panel is inserted at the drop line, uses the same page picker and import preflight, and is one undo step. A page can be deleted explicitly: its items and page state are removed and later pages keep their stable IDs. Page reorder and page insert are also one undo step each; deleting and duplicating a page remain explicit and cannot be undone. If a dropped drawing accepts the managed-copy recommendation, that copy is a later history boundary, so Undo does not remove the import; see F-076.
- Page status badges derive from project and source state only. **OCR missing** is shown for TIF pages, which are always scans; a scanned PDF page has no cheap way to prove that its text layer is empty, so it is not badged until OCR has run and stored a result. **Source changed** appears only after a completed source-file check, and reordering or dropping a drawing is disabled while a status filter hides pages.
- Import pages from another project appends pages unless an insertion position is chosen and creates one destination layer per source layer identity, shared across the imported pages. The source project is read-only. A preflight lists pages, items, references, unreadable files, skipped pages, checksum warnings and page-count changes before anything changes. Imported pages keep optional source-project and revision provenance; it is context, not a signature. The revision hash is computed from the raw project file bytes from 0.25.0 onward; pages imported by an older release keep their historical decoded-text hash and are not rewritten. Provenance stores the source project's stable ID, not its display name, so Properties and Markups show a shortened ID; adding the name needs a later additive field or schema change (F-083). Only plain `.gridscalr`/JSON files are supported; extract `.gridscalr.zip` packages first. Import previews show the page background, not the markups. Undo keeps the imported PDF proxies in memory until the project is closed or replaced, which makes redo immediate.
- Custom count types use one of the five built-in vector glyphs. Uploaded or custom-drawn count artwork is not supported. A count can represent several pieces with **Pieces per object**.
- Count schedules for doors, windows and fixtures group counts by type, category and room. They do not store width, height, fire rating or other door/window schedule attributes; that remains a separate future feature.
- Statutory Swedish area classifications such as BTA, BRA, NTA and LOA are not calculated. Categories and rooms are user-defined grouping labels, not a statutory area model.
- The 1.0 Windows and macOS builds are unsigned. Windows shows SmartScreen warnings and macOS requires the user to approve the app through System Settings → Privacy & Security. Verify published SHA-256 checksums before running a download.
- **The macOS artifact is verified in CI, not on Apple hardware.** The macOS release job mounts the DMG, confirms `GridScalr.app` and its executable are present, proves `lipo -info` reports `x86_64` and `arm64`, matches `CFBundleShortVersionString` to `package.json` and inspects the portable `.app.zip`; the `checksums` job then verifies the merged `SHA256SUMS.txt` against every downloaded artifact. No physical Apple-hardware install has been verified: Gatekeeper acceptance through **System Settings → Privacy & Security**, dragging the app to Applications, a Finder double-click and the `.gridscalr` association on macOS are untested. The artifact must not be described as hardware-tested, and a Mac in the project is the only way to close this gap.
- The full user guide and workflows are English-only in 1.0. The Swedish UI includes a Swedish quick start and an explicit English fallback for the full guides.
- The symbol library is built in and vector-only: 52 facility signs and 156 stroke-only schematic symbols. Custom symbol uploads and symbol quantities in the procurement report are not supported yet. Symbols can be resized by dragging a corner. Tags are free text and are never numbered automatically. The pictograms are original vector interpretations, not certified SS-EN ISO 7010 reproductions and not reproductions of SS-EN ISO 14617, IEC 60617 or any other named schematic standard.
- Quantity reports are available as CSV, XLSX and PDF. CSV defaults to the app locale (Swedish uses semicolons and decimal commas) and can switch to Interchange (RFC 4180) in Preferences. XLSX uses numeric cells and is unaffected.
- The reference pane is read-only and shares zoom and pan with the primary canvas. Its page can follow the primary page or be set independently, but there is no independent zoom, no second reference pane and no editing in the reference pane.
- Revision comparison compares measurement and markup data plus the rendered source pages. A raw PDF drawing reference has no markup data, so it supports side-by-side, overlay and a visual comparison PDF but no difference list. Neither mode performs a semantic diff of the PDF's raw vector operators.
- A revision comparison opens the reference project's source drawings as well as the project file. If those drawings have moved, the reference cannot be loaded until they are restored or the project is reopened from its original location.
- Radius, diameter and arc measurements are reported as **length** quantities; they do not create separate quantity types.
- Slope is measured from the two drawn points (rise over run). There is no elevation input for a slope between two real-world levels. Volume depth is entered in the project length unit, not measured from the drawing.
- OCR uses the bundled English (`eng`) and Swedish (`swe`) Tesseract models only. Other languages are not available, and OCR quality depends on scan resolution, contrast and skew.
- OCR runs on demand and can take several seconds per scanned page. The stored OCR index makes later searches fast, but re-running OCR replaces the page's stored words.
- While a project is open, source-file status checks that each drawing still exists and compares its byte size with the size recorded when it was linked. A change that keeps the same byte size is only detected by reopening the project or by the normal checksum check on open.
- Project saves replace the file with a single rename after flushing a temporary file. A folder or file system that cannot rename over an existing file, such as some read-only or network shares, refuses the save and keeps the previous project; save locally or use **File → Save a copy…**.
- Automatic rolling backups are stored in the local app data folder, keyed by project ID. They keep between 2 and 10 recent saves per project (default 3, set in **Preferences → Data**), are never added to recent files or packages, and are not uploaded or synced. Deleting them removes only the app-data copies; use **File → Save a copy…** when a portable backup is needed outside this computer.
- The project status popover reads the rolling backup list once when it opens, so a backup written while it is open appears on the next open. The last save time is the project file's modification time: a project opened from disk shows the previous save, and a browser-fallback download has no file time. A failed backup-list read is shown as no automatic backup rather than as a separate error, and the popover does not poll or refresh on a timer.
- A restored backup resolves relative drawing links from the project path recorded with that backup, then from the folder of the open project. A backup taken before the origin path was recorded still resolves through the open project's folder. A drawing that cannot be resolved is listed before the restore starts and must be located explicitly; GridScalr never substitutes the stale absolute path that the backup also carries. A backup restored on a computer without the drawings still needs each drawing located by hand, and a located drawing is stored as an absolute reference because its new relative link is unknown.
- Project packages are standard unencrypted ZIP files. GridScalr does not encrypt or cryptographically sign them; the manifest checksums detect corruption and accidental changes, not deliberate tampering. Each managed drawing is included once; a package is a transport copy and does not change the live reference or managed-copy mode.
- Original TIF scans and quantity/drawing exports are opt-in when packaging and are off by default. A schema 27 colour scan always travels as its derived cache under `derived/`, and its original scan is then never included; the manifest lists the cache with `kind: "derived"` so the form is stated. An embedded TIF may still include its original scan under `source-scans/`. A scan is never carried in both forms.
- Packaging and open-package extraction require the desktop app. In the browser fallback the commands are visible but disabled with a desktop-only note. Packages can still be unzipped manually and the `.gridscalr` file opened with **File → Open project…** in the desktop app. The browser fallback also cannot write a cache beside the project, so a colour scan downloaded there keeps its derived PDF inside the project JSON.
- Optional package exports are generated in memory before the ZIP is written. Very large drawing exports can take a while and need temporary memory, but the source PDFs themselves are streamed in Rust.
- A project file is limited to 256 MB and one opened source PDF/TIF to 1 GiB. A larger file fails with a localized message and the open project is left untouched; the browser fallback checks the picked file size before reading.
- A project package is limited to 2 GiB uncompressed, 1 GiB per entry and 2 GiB for the ZIP file itself, and one managed copy is limited by the same 1 GiB source cap as an opened drawing. The package dialog shows the expected uncompressed size before anything is written, package creation refuses a package over the 2 GiB limit or a destination without the size plus a 64 MiB reserve, and open-package extraction applies the same two checks. A large package still needs that free space temporarily because the previous extracted folder is kept until the new one is verified.
- A crashed save can leave a flushed temporary sibling next to the project, and a crashed package extraction can leave its staging folder beside the project. Opening a project removes both: only names that exactly match the app's generated patterns (`.<name>.<pid>.<stamp>.<counter>.tmp` or `.copy`, and `.<name>.extract-<pid>-<stamp>` folders), only entries older than ten minutes, and never an entry carrying the running process's own id. A `.<name>.previous-<pid>-<stamp>` folder from a replaced extraction is kept, because it holds the folder the user replaced, and a crashed save in a folder that is never opened again stays until the next save or open there.
- A project may reference a drawing outside its own folder. A dismissible warning names those drawings and offers **Copy into project** and **Relink**; the reference itself stays valid and is never rejected. Only open projects from a source you trust, because a project can point at any file you are allowed to read.
- Package extraction refuses unknown archive entries. Do not add extra files to a package ZIP unless you also update its manifest; manual unzip and opening the project is not affected.
- Recovery autosave needs local IndexedDB or, as a fallback, localStorage space. It keeps the latest snapshot per project plus one previous, and up to ten structural checkpoints per project, inside an explicit byte budget: **64 MiB per project and 256 MiB for the whole recovery store on this computer**. A write that would exceed either budget prunes the oldest records first, so the store cannot grow without limit and cannot exhaust the browser's IndexedDB quota before recovery matters. The newest autosave and the newest checkpoint of every project are never pruned by rotation: a project whose single snapshot is larger than 64 MiB keeps those two records and nothing else. The budget counts the serialized snapshot bytes; record metadata adds a few hundred bytes per record and is bounded by the twelve-record count limit. The recovery center shows the total and per-project size, diagnostics report the same totals without names or paths, and both `Help → Diagnostics → Copy diagnostics` and the center list each record's size. When storage is still full, for example because another site uses the same quota, GridScalr names the file save and the recovery center as the next actions, and the **Recovery storage full** chip opens the center. The localStorage fallback has its own small quota (about 5 MB), so a large project falls back to that actionable message instead of keeping a partial snapshot. Pruning uses only the local store and never touches project files or drawings.
- The byte budget is not derived from `navigator.storage.estimate()`. On an origin with a very small quota the store can still hit the browser limit before 256 MiB, and the quota-failure message remains the fallback.
- A record written before the byte budget existed has no stored snapshot size; the recovery center measures it once from the serialized string when it is listed. New records persist the size at write time.
- Autosave is an app-level preference, not a per-project setting. It is on by default and writes at most one snapshot every 15, 30 or 60 seconds after a change. Turning it off or pausing it for the session stops periodic snapshots immediately, so an app crash loses every edit since the last manual save or structural checkpoint. Checkpoints before page, source and import operations are still written while autosave is off or paused. A pause resets when GridScalr starts again.
- The sidecar project lock (`<project>.gridscalr.lock`) is advisory, not a guarantee. It warns when another live instance has the project open and defaults to view-only, but a cloud client or a sleeping laptop can delay the heartbeat. A crash can leave a stale lock for up to five minutes; a stale or corrupt lock never blocks opening and can be cleared explicitly. The conditional save remains the actual protection.
- A view-only session disables every project mutation. Pan, zoom, search, the reference pane, export, package and **Save a copy…** still work; a normal Save and Save As are refused. Running OCR is disabled because it stores a page index in the project; text already indexed remains searchable. **Take over to edit** re-checks the lock before editing is enabled. The original project file is not written from a view-only session.
- The integrity validator proves internal referential consistency, not external truth. The project doctor reports source availability separately, so a missing or changed drawing is a warning with relink and copy actions, never a save error. The validator still cannot confirm that a referenced drawing is the correct revision, that a PDF still matches its checksum without reading it, or that quantities and measurements are commercially correct.
- Explicit repairs cover duplicate IDs, dangling references and stale OCR. The doctor can apply them as one selection or as a subset, and the preview is generated from the same plan that is applied, so the listed renames and removals match the saved repaired copy. Other problems are reported but not rewritten automatically, including image assets whose MIME and data disagree, invalid image or text-box geometry, dangling report metadata and invalid optional provenance. A repair that would change nothing is not applied. Unreferenced managed drawings are handled by the doctor's explicit cleanup, not by a repair. Review the remaining issues manually or save a repaired copy only after they are acceptable.
- The doctor's preview lists at most 20 concrete changes for a large repair, and diagnostics export lists issue codes and counts rather than the full planned rename set. A very large duplicate-ID repair must therefore be reviewed in the saved copy, not only in the preview.
- Duplicate-ID repair keeps the first occurrence of an ID and renames later ones. References that used the duplicated ID cannot be attributed to a specific occurrence and remain attached to the first one. Review affected pages and markups before relying on the repaired copy.
- A load report and the project doctor use stable technical codes for dropped or repaired load entries. They describe what normalization did; they do not recover data that was never valid.
- The sidecar lock, file watcher, view-only enforcement and explicit take-over are desktop-only. The browser fallback keeps the scoped IndexedDB recovery store and downloads on Save; it has no lock file or disk-change banner.
- The desktop window draws its own title row on Windows and Linux, so the Windows 11 snap-layout flyout on hover over the maximize button is not shown. Aero snap by dragging the window to a screen edge, double-click to maximize and the system menu still work. macOS keeps the native traffic lights and title bar behaviour.
- File associations are registered by the installers only. The portable `gridscalr.exe` and the AppImage do not claim `.gridscalr`, and Linux associations depend on the desktop environment reading the installed `.desktop` file. GridScalr never claims `.pdf`.
- The AppImage does not yet pass the opened file, because Tauri's AppImage desktop entry omits the `%f` argument ([tauri-apps/tauri#16014](https://github.com/tauri-apps/tauri/issues/16014)). The `.deb` and `.rpm` packages ship a custom desktop entry and do pass it.
- Single instance uses a per-user channel (D-Bus on Linux). In a session without a session bus, or when the app is started from two different user accounts, a second launch starts a second window instead of focusing the first.
- The remembered window position is only restored when it still intersects a connected monitor; otherwise the operating system places the window. Window geometry is stored per user account and is not part of the project file.
- The packaged smoke test drives the app from inside: it covers launch, opening the demo, saving, reopening and the unsaved-changes prompt. It runs against **debug** builds in CI, including on macOS on every pull request. The release workflow never launches a packaged binary: the smoke commands are compiled into debug builds only (F-037), so a release binary would ignore the flag and wait forever (F-074). The macOS release artifact is therefore verified structurally (DMG mount, universal binary, bundle identity, version and hashes) instead of by launching it. Native file dialogs, menu clicks and drag-and-drop are not automated on any platform, and macOS has no WebDriver (`tauri-driver`) support at all; those paths stay in the manual install checklist.
- The demo project is copied to the app data folder on first use, and edits are saved to that copy rather than to the bundled fixture. Delete the `demo` folder under the app data directory (for example `%APPDATA%\com.gridscalr.desktop\demo` on Windows or `~/.local/share/com.gridscalr.desktop/demo` on Linux) to restore the bundled version. The demo is not available in the browser fallback.
- The language selector covers the interface, reports and export headings. A low-level filesystem failure shows a localized message and keeps the operating system's technical detail as a separate line.
- The static boot fallback in `index.html` is English until the selected catalog loads; it is replaced before the app starts, and startup failures after that point use the active language.
- Diagnostics and the local event log are stored on the computer only. There is no telemetry, crash reporting or upload, and the log keeps the last 80 entries with paths, drawing names and labels removed. Startup failures before the log is available are shown on the boot screen instead.

The position is not stored: a reopened window returns to the centre, and the window cannot be moved or resized from the keyboard. A click outside the window no longer dismisses it. Destructive confirmations revalidate their object by stable id at confirm time and refuse with an explanation when it changed; the listed confirmations in the ADR are covered, and a new destructive confirmation must opt in with a `target`. Global shortcuts pause while focus is inside a dialog, not while one is merely open.

The clearing path is the Tauri 3 / GTK4 migration in [#270](https://github.com/MajorJohnDoe/gridscalr/issues/270); [#21](https://github.com/MajorJohnDoe/gridscalr/issues/21) tracks the advisory until it lands.

## Large-project performance

The **reference project** is generated deterministically by
`npm run bench:large` from the demo takeoff: 150 pages, 15,000 markup items,
60 embedded images and a serialized project around 8 MB. Source PDF bytes are
not duplicated in the benchmark; the Rust package tests exercise the streaming
1 GB path separately. Override the shape with `GRIDSCALR_BENCH_PAGES`,
`GRIDSCALR_BENCH_ITEMS` and `GRIDSCALR_BENCH_IMAGES`.

The budgets below are measured with Chromium, Node 24 and the browser fallback.
`npm run check:performance` runs them in CI on a 40-page, 4 000-item budget
profile and fails on a breach;
`GRIDSCALR_PERF_PROFILE=reference npm run check:performance` runs the full
150-page reference project. A missing measurement fails: an unmeasured budget is
not a passed budget. Run the full profile on each release platform before a
release candidate; a regression beyond a budget blocks the release. The memory
row stays a manual desktop check: the browser fallback and WebKit report no
working set, and `performance.memory` exists on WebView2 only.

The measured baseline for each optimization phase, with the commit, machine
profile and run-to-run variance, is in
[`docs/performance/history.md`](performance/history.md).

| Measure | Budget | Notes |
| --- | --- | --- |
| p95 edit latency | under 100 ms | A single history-tracked mutation in the reference project. |
| Project open | under 10 s | Parsing and store setup; PDF rendering is separate and progressive. |
| Autosave | under 2 s | Debounce plus the IndexedDB recovery write. |
| Page switch | under 100 ms | Store page change without waiting for a render. |
| Memory | under 2 GB | Desktop app working set while the reference project is open. Manual: the performance panel reads `performance.memory` on WebView2 only, so macOS and Linux have no in-app working-set number. |
| UI freeze | under 2 s | Longer operations need progress and cancel. |

Undo history is adaptive: it keeps up to 80 snapshots for small projects and
shrinks towards four snapshots when a single serialized snapshot exceeds the
48-million-character budget. A very large project therefore keeps a shorter
undo history rather than exhausting memory.

The Markups table renders only the rows near its viewport, canvas rendering
skips items outside the visible viewport, and autosave stores one serialized
snapshot with a skip when nothing changed since the previous write. These are
the tested 1.0 limits; there is no promise of unlimited project size.

### Primary canvas tile cache

The primary canvas rasterises its page crop as 512 CSS px tiles in visible-first
order and paints the first completed tile immediately. Tiles are anchored to the
**page**, not to the visible crop: a tile is identified by its page column and row
at the current render scale, so a pan keeps every tile that is still on screen and
renders only the newly exposed edge. Two things stay visible while the exact
tiles are being prepared: the previous complete raster underneath the new
composition, and, when that raster does not cover the new view (a zoom out or a
large jump), one coarse pass of the same crop at 45 % of the device scale. The
coarse pass costs a few milliseconds and shows a soft copy of the drawing
instead of an empty sheet until the exact tiles arrive. During a long gesture the
markup layer is redrawn for real at most every 120 ms or once the view has moved
30 % of the smaller canvas side, whichever comes first, and stays on the fast
blit in between. The page raster is skipped while the bitmap on screen already
covers the visible page area at the same page, zoom and pixel density, and
otherwise starts at most every `clamp(1.5 × the last measured raster cost,
220 ms, 600 ms)` while the gesture runs, so newly exposed drawing fills in
during the pan instead of only at pointer release. A debounce alone was reset by
every wheel event, which is why a held scroll previously rendered nothing until
it stopped. The tile cache
is capped at **128 MiB of RGBA pixels** (`TILE_CACHE_BUDGET_BYTES` in
`src/features/tileCache/model.ts`). At 1440 × 900 that is about ten views at
DPR 1 or two to three at DPR 2; the phase 4 probe measured 10.2 MiB steady state
on both performance shapes. When the cap is reached, tiles farthest from the
current viewport are evicted first, and the tiles of the current view are never
evicted.

The full-page crop remains the fallback and the only path for the reference
pane, split view, comparison and every read-only canvas's PDF raster. It is also
used for the life of the page when `createImageBitmap` or `OffscreenCanvas` is
missing, so a WebKit runtime without both APIs never attempts a tile; a tile
render error falls back to the full-page path. The packaged debug probe
([`testing.md`](testing.md)) compares the tiled and whole-page rasters on the
real platform runtimes. The packaged local Linux WebKitGTK run used the tiled
path at zoom 1, 3 and 6: zoom 1 and 6 matched, while zoom 3 differed on 1.006 %
of pixels (max delta 156) and is recorded as `mismatch` under the tightened
verdict. The CI Ubuntu WebKitGTK job did not use the tile path at any zoom, so
those levels are `not-used`, not passes. On macOS WKWebView the final CI run used
tiles at zoom 3 and 6: zoom 6 matched (0.110 % differing, max delta 1), zoom 3
differed on 1.179 % with max delta 119 and is `mismatch`, and zoom 1 did not use
the tile path under the first-tile cost rule. A preceding macOS run used tiles at
zoom 1 and differed on 4.008 % of pixels (max delta 161). The WebKit zoom-3
differences have a page-wide bounding box and no blank or integer-offset tile;
the best 1-pixel shift moves the Linux ratio from 1.006 % to 0.987 % and the macOS
ratio from 1.179 % to 1.118 %, which does not materially explain the difference.
Tiles stay enabled. The Windows WebView2 differences (2.330–4.675 % at rest, no
blank block, no material integer offset), the earlier high-DPR macOS zoom-1
difference and the max-delta failures above are tracked as F-150
([#389](https://github.com/MajorJohnDoe/gridscalr/issues/389)) and are not yet a
recorded platform fallback.

Tiles are abandoned for the rest of the session once the first tile costs more
than 30 ms, because PDF.js re-walks the page operator list per tile and on a dense
drawing a tile can cost as much as a whole crop; the measured case was 88 ms per
tile against 205 ms for one crop. Tiles trade one monolithic raster for several smaller rasters. On a small crop
the first tile can cost about as much as the monolith because PDF.js walks the
whole page operator list for every render; the measured win is the lower total
raster work during a zoom stream (30–38 % in the phase 4 probe) and the bounded
transient cache, not a lower first-tile latency (F-148). The composed tile raster
is not bit-identical to one crop: a small number of antialiased edge pixels
differ (≤ 0.17 %, max channel delta 10 at the fit view), with no seam or offset.
`npm run test:visual` passes with no baseline change.

### Display levels (scanned drawings)

The primary canvas also keeps **one whole-page bitmap per page and zoom octave**
in memory, capped at **128 MiB** (`LEVEL_CACHE_BUDGET_BYTES` in
`src/features/displayLevels/model.ts`). The octave index is `log2(zoom × device
pixel ratio)` rounded up. A view at the octave's own scale is served from the
level with no render, because that bitmap was rasterised at exactly the view's
scale and is the exact image; a pan that leaves the crop margin and a return to a
visited octave then blit it instead of rendering the PDF again. Inside an octave
band the level fills the gesture and the exact crop renders once on release, so
the settled image is never softer than the crop it replaces. The phase 2 probe
measured 4 → 0 renders for a five-second pan at an octave scale and a `level-hit`
with no render on a zoom-back, with 0 differing rest pixels against phase 1.

A level is only built when its whole page fits the caps (20 Mpix and an 8192 px
side) and can reach the view's own scale, so a level is never a soft substitute
for the exact crop; when none qualifies, the phase 1 path (crop render, coarse
pass, tile cache) applies unchanged. On the reported 2531 × 1685 pt scan that
means levels cover `zoom × dpr ≤ 2`, and a higher zoom still pays one crop render
per view. Levels are display state only: memory only, dropped when the project
closes, never measured, printed, exported or written to the project file, and
keyed by the loaded document identity so a replaced source can never draw the old
drawing. Eviction is least-recently-used except for the level being drawn, so a
single level larger than the budget can exceed it until the next view; one level
is capped at 20 Mpix (80 MiB), which bounds that overshoot.
